# DSH 零脉业务逻辑

> 面向运营者与协作者的系统性说明：零脉是什么、各配置层管什么、一个任务从需求到收口怎么走、容量怎么调度、质量怎么把关。行为细节以 `openspec/specs/` 合同为准；安装与命令见《安装运维手册》。

## 1. 零脉是什么

零脉（PactFlow）是 DSH 的插件，把「多 Agent 协作完成一个开发需求」做成可审计的流水线：

- **需求（Need）** 是业务入口：一段要交付的目标（如"给数据模块补单测并通过构建"）。
- **DAG** 把需求拆成有依赖关系的节点，前置节点的产出（提交）是后续节点的输入。
- **Run** 是一次节点执行：由一个 **Worker**（K3s 里的 Harness CLI 容器）认领，产出代码提交与**验证证据**。
- **收口（Closing）** 是需求成果固化时刻：候选提交在通过质量门禁后合并推送，此后工作成为合同交付。

角色分工：

| 角色 | 是谁 | 关心什么 |
|---|---|---|
| 运营者（Operator） | 人，经 Web UI | 配资源、定门禁、看证据、做决策（恢复/保留现场/收口） |
| Agent（DSH 会话） | 宿主里的模型会话 | 经零脉工具读写需求、推进节点、登记验证 |
| Worker | 集群里的 Harness CLI Pod | 只做被派发的节点任务，产出提交与证据 |
| 宿主（Host） | 插件运行时 | 强制合同：准入、预算、门禁、凭证、清理 |

宿主不信任 Worker/Agent 的自我声明——这是贯穿全部设计的基线（见 §6）。

## 2. 两层配置模型

### 2.1 全局基础设施（设置 → 插件 → 零脉基础设施）

七类资源卡，前四类是"素材"，第五类是"组织"，第七类是"内容外置"：

1. **K3s 集群**：在哪里跑（kubeconfig + context + namespace）。
2. **Harbor 镜像仓库**：Worker 镜像从哪来。合同要求**单仓库存全部四类 Harness 镜像**、按标签前缀识别（`claudecode-ox_v1` / `codex-ox_v1` / `opencode-ox_v1` / `dsh-ox_v1`）；测试通过即自动同步四个 Harness 模板。
3. **Gitea**：任务分支/交付仓库所在的 Git 服务（按项目 remote 自动匹配）。
4. **Harness 模板**：一个模板 = 某种开发工具的 Worker 形态（镜像 digest 钉死 + CPU/内存规格），**不绑模型**。
5. **模型连接**：可用的模型服务（协议 + URL + 凭证 ref + 模型 ID）。与 Harness 独立，运行时按协议配对。
6. **执行资源池（Worker 并发与调度）**：`池 = 集群 × 允许的 Harness 白名单 × 并发总量`。**并发是池级总量**（不分 Harness、所有使用该池的项目共享），超出自动排队。
7. **对象存储（artifact store，第七类）**：大内容外置的 S3 兼容存储（endpoint + bucket + path-style + 凭证 ref）。项目可绑定一个存储，worker 与宿主把超长内容（执行日志、大报告）外置为 `artifactRef` 地址，有界通道只传地址与摘要；删除被项目引用的存储失败关闭。

引用关系：池 → 集群 + 仓库 + 模板白名单；Agent 组合 → 池 + 模板 + 模型；项目 → （可选）对象存储。

**生效时机**（`infrastructure-probe-freshness` 合同）：探针/只读发现/删除影响读**当前已保存**配置，保存即可测；**运行时资源**（池、K3s client、派发准入）**重启 Profile 后生效**——保存新池后，正在运行的宿主派发行为不变，重启才接入。

### 2.2 项目配置（零脉项目面板，每工作区）

- **Git 仓库**：以工作区磁盘上的真实 Git 为单一事实源（不存副本）。远程变更走**对账（reconcile）+ 迁移**流程确认，避免面板与磁盘漂移。
- **宿主验证配置**：本项目的验证命令登记册（构建/测试/部署检查）。只登记不执行；任务运行时模型按编号执行，成功留档为**验证证据**。
- **收口最小验证策略**：勾选哪些验证是收口硬门槛（见 §6）。
- **宿主基线**：宿主自有断言命令，存于任务仓之外（owner-only）。
- **Agent 组合（Agent Profile）**：`Harness 模板 × 模型连接 × Worker 数量`。数量是**本项目声明需求**（1–12），不是预留；实际并发由池仲裁。

## 3. 任务执行流水线

一个节点的完整旅程：

```
需求 → DAG 节点就绪（依赖满足）
     → 统一准入（容量/状态/预算检查，见 §4）
     → resolveExecution(池, 模板, 模型)：协议兼容配对，注入模型凭证
     → K3s Job（Worker Pod）
        · 镜像 = 模板 digest 钉死的 Harness 镜像
        · /opt/dsh-pactflow/worker.sh 由 ConfigMap 挂载
        · 模型经环境变量注入（Anthropic: ANTHROPIC_BASE_URL/AUTH_TOKEN；
          OpenAI 系: OPENAI_BASE_URL/API_KEY），凭证来自 K3s Secret
        · 代码经 Git Secret（ssh 私钥 + known_hosts，0440/strict）拉取任务分支
        · 代码输入 = 前置节点已验证成功的提交（code-input 合同，防陈旧）
     → Run 终态：成功（含 gitResult 提交/分支）/ 失败（可重试，受预算约束）
     → 证据落账（验证执行记录、digest、时长）
     → 节点全绿 → 收口（§6）→ 推送远端
```

失败与预算：节点重试受重试预算约束；**预算耗尽进入持久暂停（paused）**——落账、界面可见、派发指名拒绝，等待人显式恢复（`resumeNode`）。Run 级失败现场可按保留策略留档取证。

## 4. 容量与调度语义

两层配额，**原子获取**，超限**排队而非失败**：

| 层 | 配额 | 粒度 |
|---|---|---|
| 项目层 | 每个 Agent 组合的 Worker 数量（1–12） | 本工作区内，FIFO |
| 全局层 | 池并发总量 | 所有项目共享，FIFO（项目内队列 128 / 全局 512 上限） |

语义要点（运营者决策已裁决并合同化）：

- 池并发是**总量**，不按 Harness 分列；要"某 Harness 独占 N 并发"就单建只含它的池。
- 项目声明的数量**可以超过**池上限（声明的是需求，不是预留）：池 3、组合写 5 → 同时最多 3 个槽，其余排队。
- 跨项目不互相抢占失败：别的项目占满时，你的任务进队列等槽位释放。

## 5. 连通性与探针

每张资源卡有「可用性测试」，日志分阶段（校验配置 → 连接 API → 访问资源 → 领域检查如镜像完整性）。合同要点：

- **保存即可测**（读当前已保存文档）；测试日志必须收敛到终态。
- 模型探针（`model-probe-auth-fallback` 合同）：Anthropic 协议首发 `x-api-key`，**仅 401** 时以 Bearer 重试恰一次（兼容火山方舟等 Bearer 网关）；路径自动补 `/v1/messages` 与运行时一致。OpenAI 系协议直接 Bearer。
- 模型列表自动发现只支持 OpenAI 形状；Anthropic 协议一律**手动填模型 ID**（端点能力所限，非故障）。

## 6. 质量门禁：收口三层防线

收口 = 把需求成果固化成提交并推送。宿主不信任执行侧，三层递进：

| 层 | 配置处 | 谁执行 | 挡什么 |
|---|---|---|---|
| ① 验证证据 | 宿主验证配置 | Worker/模型按编号执行 | 「没验证过」——收口要有真实执行记录 |
| ② 最小验证策略 | 收口最小验证策略 | **宿主**核对每交付物的必需证据 | 「验证过但不是必须的那些」——缺失逐项指名阻断，模型不可修改 |
| ③ 宿主基线 | 宿主基线（owner-only） | **宿主**在候选提交上**先于**任务验证执行 | 「任务仓内的验证被绕过/篡改」——命令存在任务仓外，Worker 够不到 |

三层合起来回答：证据由谁产生（①）、哪些证据必须存在（②）、独立于任务的最终防线（③）。

## 8. 安全与凭证边界

- 一切密钥（模型 key、Harbor、Gitea token、SSH 私钥）只进 **DSH Credentials**（或 K3s Secret），配置里仅存引用（ref）；原始凭证禁入 Session Log、Remote payload、Git、argv、截图与持久日志。
- 私有 CA 环境需给宿主进程配 `NODE_EXTRA_CA_CERTS`（Node 不读系统钥匙串）。
- Worker Pod 最小权限：非 root、全能力剥离、SA token 不挂载、只读挂载输入。
- 卸载前有 drain 检查（`safeToUninstall`），跨主机文件锁失败关闭（绝不夺取疑似活主）。

## 9. 运行态与异常处置速查

| 现象 | 含义 | 处置 |
|---|---|---|
| 节点显示「已暂停（等待决策）」 | 重试预算耗尽 | 人显式恢复（resumeNode） |
| 任务排队不动 | 池槽被占满（跨项目共享） | 等待 / 调池并发并重启 / 换池 |
| 外层测试红、卡内测试绿（历史） | 已修复的配置快照问题 | 现两路同读已保存配置，不应再现；再现即缺陷 |
| 收口被阻断 | 门禁证据缺失（逐项指名）或宿主基线失败 | 补验证 / 检查基线命令输出 |
| Worker 镜像拉取失败 | pull secret 或镜像 digest 不符 | 核对池的拉取密钥与模板 digest |
