## 2. 本轮源码核查补充发现（GPT 未提或需强化）

- **N1（高）**：`package.json` 新增的四个 B 类验收入口（`test:real-probe-ledger`、`test:real-crash-restart`、`test:real-approval`、`test:real-web-gate` 相关的 `pactflow-k3s-ttl`）其 spec 仍是 `expect.fail('skeleton: …')` 骨架。启用环境变量后不是“通过”，而是断言失败。**当前不能把 B 类③④及 TTL/账本/跨重启计为已覆盖**；同时 `run-real-k3s-batch.mjs` 的两个 stage 是显式未实现。建议：要么实现，要么在脚本与文档中显式标注 `not-run`，禁止出现在任何“验收通过”汇总里。
- **N2（中）**：`evidence:collect` 依赖持久目录 `~/.pactflow-acceptance-evidence`，但 `impact-list.schema.mjs` 未被任何 runner 导入；授权与影响清单未在执行入口被强制（对应 R09 后半）。建议把影响清单纳入 runner 的准入前置。
- **N3（中）**：实施状态文档自身矛盾（第 196–201 行称决策已定、真实 Gitea/K3s 通过；第 204–205 行称决策待定、真实验收未运行）。采纳 R10 的 CURRENT_STATUS 单一视图，旧段落保留为批次历史。
- **N4（低）**：`dsh-pactflow.zip`（1.4MB）位于仓库根且未跟踪，易被误提交。建议加入 `.gitignore` 或移出仓库。
- **N5（低，采纳 A10 边界）**：`fad4d32` 起探针把 thinking/reasoning 回退为语义来源。用于连通性诊断合理，但须与“可交付答案”分级，不能把任意 reasoning 文本当成用户可验收成果。

## 3. 合并后的优化方案

按“先机器可验收、再信任边界、再交付正确性、再真实验收、最后长期项”排序。每项沿用计划 §15.3 规则：先失败后通过、`pnpm run check` + `git diff --check` 收口、断言与超时不为通过而削弱。

### 第 0 批 · 让“完成”可机器判定（脚本层，成本低、收益高）

| ID | 内容 | 验收 |
| --- | --- | --- |
| G1 | 拆分 `evidence:collect`（采集）与 `evidence:verify`/`acceptance:gate`（门禁）。gate 按版本化清单拒绝 failed/unknown/缺工件/错 hash/旧 commit/重复 target/缺 ZeroProof/零测试/跳过 | 投喂上述反例均不得通过；通过用例需工件摘要一致 |
| G2 | 修 schema：`blocking` 真可选；`validateZeroProof` 增加语义（本批已确认拥有资源已收尾、外部既有资源未受影响），不以空 namespace 代替；`impact-list` 允许空数组、按 kind 强制 `expectedUID`/`expectedCommit` | 正反例对照 |
| G3 | 实现 `run-real-k3s-batch.mjs` 的 `ttlStage`/`zeroProofStage`；批次责任与资源意图先持久化；无论主测试成败都进入有界清理/对账；TTL 观察与主动清理分开 | 离线正反例；失败也产出清理结论 |
| G4 | 报告不再在 finally 删除；通过/失败报告复制到持久验收目录并附源码/产物摘要；生成单一 CURRENT_STATUS（含 N3） | 失败报告可事后复核 |
| G5 | 声明式 TestSuiteSpec（凭证引用/能力/授权范围/环境标志/时限/预期报告/清理类别），专用与全集 runner 共用；开发态 `link:` 通道与发布态固定基线通道分离 | 入口合同一致；release 通道不隐式用 sibling |
| G6 | 四个骨架 e2e 与已声明脚本对齐：实现或显式 `not-run` 标注（N1、N2） | 无“骨架冒充通过” |

### 第 1 批 · 关闭信任与破坏边界（P0）

| ID | 内容 | 验收 |
| --- | --- | --- |
| H1=F01 | Agent 只提交登记的 `providerId` + 仓库身份；Host 由已批准配置解析 endpoint/credentialRef/认证方式；校验 remote↔Provider↔repo 一致；跨源重定向不带授权；HTTP 仅限用户显式允许的本地例外 | 非登记 origin、错 repo、错配 ref、HTTP 降级、redirect 换源，全部在发出带凭据请求前拒绝；正常连接仍通过 |
| H2=F02+R07 | 建立本次 create operation 的 owned 集合（仅服务端返回 UID 的对象）；UID 前置删除，不要求先有 ownerReference；409 对象从不属于本轮，不删；删除超时保持 outcome-unknown 并保留责任 | 409 不删既有对象；检查后被同名替换不删；超时不清账、不伪装成功；本轮确定孤儿可回收；404 幂等 |

### 第 2 批 · 交付正确性（P1）

| ID | 内容 | 验收 |
| --- | --- | --- |
| H3=F07 | 本地 Git 派发统一走 `admit → freeze → claim → execute → verify → settle → release`；首次 await 后到 claim 前复查取消/workspace/config 版本/操作身份；释放由幂等 handle 管理 | 本地/K3s 同受限时均遵守准入；启动盘点能挡住本地；取消排队不 claim |
| H4=F05 | 交付身份锁定精确 Gitea merge SHA，独立目录复验该 tree；release 记该 SHA；祖先检查降为附加证明 | 已验证 integration 但精确 merge tree 失败时拒绝完成；main 再前进不错误绑定 |
| H5=F06 | 优先引入一次 finalization 事实事件（release + Need 终态同投影）；若暂不改格式，重试先读取并复用既有精确 release，再推进缺失阶段；closing 分配稳定 operationId，清理门禁绑 finalized | 各外部返回/事件 append/清理前后注入失败重启，得到唯一 release 或显式待人工，不重复合并、不永久卡普通重试 |

### C 类（阻断于上游，持续维护）

- 官方 DSH 兼容矩阵（版本/commit、Session 格式、事件生产者能力、Approval 审计、Subagent cwd、Remote/slot）；当前官方已至 `v0.1.5-alpha.2`（2026-09-09，Session V3 + Web 面板 API），须重核而非沿用 9-06 结论。
- 升级路径：真实旧数据（含已批准评审、排队/运行任务、待清理责任）→停→升级→回放→恢复→完成；旧项目不能续写时给出只读/受控迁移/阻断策略。
- 每次官方新版本发布复跑，不将历史结论当永久事实。

## 4. 需用户裁决的事项

1. **A8**：`deployed` 是否仅表示“已合并/已交付”；若改枚举语义属目标变更。
2. **严格 FIFO**：仅在用户改变吞吐目标时才调整；本方案不改。
3. **节点准入**：维持决策 1B，本方案不动。
4. **不可信代码的执行安全承诺**：是否引入独立受限环境（A4/A7 的强隔离）——涉及信任边界扩大，须裁决。
5. **本方案并入计划文档的范围与批次**（计划 owner 变更走用户确认）。

## 5. 推荐执行顺序与门槛

1. 第 0 批先做（不新增平台功能，先把“完成”变成可机器判定，且 G6 消除骨架造成的假覆盖）。
2. 第 1 批（P0 信任/破坏边界）——H1、H2。
3. 第 2 批（交付正确性）——H3–H7。
4. 第 3 批（执行统一 + 真实验收，B 类逐项授权）——H8、B1–B4。
5. 第 4 批与 C 类按需穿插。

**总门槛**：故意投喂失败/未知/错版本/缺工件/跳过/残留等反例均不得得到完整验收通过；同一产物摘要贯穿构建、测试、安装；`B`/`C` 类未运行或不通过的项在最终报告显式列出，不制造假闭环。
