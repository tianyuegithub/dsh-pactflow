# DSH PactFlow 全面评审与架构改进建议

**评审日期：2026-09-10**  
**评审对象：第二次上传的完整 `dsh-pactflow.zip`，包版本 0.2.1**  
**ZIP SHA-256：`ae9ad9bf8315c08b62d314c32bb7be9a9e5b211a5a567ce205bd69b73ab8d639`**

## 1. 总体判断

PactFlow 已不是一组提示词或简单任务看板，而是一个有实质执行能力的本地开发工作流插件：它将需求阶段、DAG、人工批准、隔离任务分支、宿主验证、Gitea 合并、K3s Worker 与恢复清理串在一起。Host 持有事实写入权、Worker 不能直接写 Session 事实、用户拥有验证配置，这些方向值得保留。

**当前主要问题不是“少几个功能”，而是几个边界尚未闭合：批准的对象、执行的输入、验证的代码、最后交付的提交，以及失败后允许清理的资源，没有在所有路径上保持同一份不可变身份。**

本次建议定位为：**已有较完整的工程基础，但仍应按受控试用/发布前加固版本管理，不宜把关键需求直接交给无人值守自动闭环。** 这不是说项目没有真实验收：文档中有真实 Gitea/K3s 通过记录，也有本地 Worker 未产生提交的失败记录；本次未独立复跑那些环境，不据此宣称它们通过或失败。

最值得优先投入的方向：把“有一套过程”升级成“每个输入、决定、副作用和输出都有可以验证的对应关系”。不建议此时改造成中心化企业平台，也不建议为了统一概念重写全部系统。

### 2.3 没有声称完成的验证

没有运行原项目完整 `pnpm run check`、完整类型检查、官方 DSH 安装生命周期、真实 Kubernetes/Gitea 或浏览器端到端验收。本环境 Node 为 `v22.16.0`，低于包声明的 `^22.19.0 || >=24.0.0`；没有 pnpm，开发依赖引用的相邻 DSH 工作树不在包内，npm registry 查询也遇到 DNS 失败。因此，独立复现必须在受支持引擎和正式装配环境下再次纳入回归。

本地单机为目标；生产使用未修改的官方 DSH，开发 fork 不成为生产解法；调研节点可在依赖就绪时提前运行；Gitea 创建结果不明时由人确认精确仓库 ID；Session 事件拥有运行事实，Workspace 配置拥有用户设置，两者不是应该强行合并的“双 SSOT”；Git worktree 和登记命令不是操作系统沙箱。

这里的 P0 指发布前必须关闭的信任/破坏边界，不是 CVSS 评分，也不意味着线上已经发生事故。P1 指能破坏交付正确性或恢复闭环；P2 指资源、可维护性与体验风险。

### F01 · 凭据引用与目标地址没有被绑定为一个授权能力

**位置：** `agent/index.ts:62–102`；`index.ts:534–610,2433–2439`；`git-workspace.ts:601–633`；`gitea.ts:323–365`。

Agent 工具允许同时提交 `gitea_base_url` 与 `gitea_token_credential_ref`。Host 在显式提供 gitea 字段时，跳过了 `infrastructure.matchGitea(remoteUrl)`；只确认该 credential ref 已配置。URL 校验只处理协议和内嵌凭据，没有要求它与登记 Provider、Git origin 和仓库身份对应。随后 Gitea Client 将真实解析到的凭据放入 Authorization 请求头。

R06 使用一个可信地址作为 Git origin、一个已登记凭据引用和另一个回环 API 地址。实际 `bindGit` 接受了组合，`verifyGitea` 把合成令牌发送到后者；登记 Provider 的 match 路径调用次数为 0。

**威胁前提：** Agent 能调用该工具并知道一个有效凭据引用，且没有额外外层授权策略阻止该调用。不是宣称已经泄露真实令牌，也不是需要给模型展示令牌明文才会出问题。

**建议：** Agent 仅提交用户登记的 `providerId`、仓库身份和非敏感选择项；Host 由已批准配置解析 endpoint、credentialRef、认证方式和允许资源。把“配置了凭据”与“允许把该凭据发给这个目标”分开校验。重绑外部域名或扩大仓库范围需要用户明确批准。连接时验证 remote 与 Provider/repo 对应；跨源重定向不能自动携带授权。HTTP 只作为用户显式允许的本地开发例外，不让模型自行决定。

**验收：** 非登记 origin、不同 repo、错配 credentialRef、HTTP 降级、重定向换源全部在发出带凭据请求之前拒绝；普通已登记连接继续通过。

### F02 · 创建阶段的私有补偿不能豁免资源所有权校验

**位置：** `k3s-worker.ts:349–458,1454–1523`，特别是 `compensateCreatedChildren`。

已绑定资源走 UID 精确删除，但创建阶段保存了 createdInputSecret/createdConfigMap 后没有把它们的 UID 作为补偿条件。输入 Secret 或 ConfigMap 创建失败时，补偿函数仍删除 `spec.configMapName` 和 `spec.inputSecretName`。因此，一个 create 409 AlreadyExists 并不意味着“我们刚创建过它”，但现实现会按名称删除那个已有对象。

R01 复现 ConfigMap create 409 后删除已有 ConfigMap；R02 复现输入 Secret create 409、成功创建资源数为 0，却仍发出两个按名称删除；R03 复现所有删除均超时，补偿返回值仍表示没有失败。虽然名称含逐运行随机片段，碰撞概率降低并不构成归属证明。

这里尤其需要修正测试假设：现有 `tests/k3s-worker.spec.ts` 明确测试了按名称补偿成功，而没有把“该对象是别人的”作为负例。增加测试数量不能弥补错误的不变量。

**建议：** 建立本次 create operation 的资源清单，只有服务端成功返回并持有 UID 的对象进入 owned 集合。对这些对象使用 UID precondition 删除，不要求它们先拥有 Job ownerReference。409 对象从未属于本轮，不删除。超时保持 outcome-unknown；通过精确身份查询/操作标识/人工确认恢复，不能把未知当作不存在或删除成功。创建意图先持久化，避免进程退出后丢失责任。

**验收：** create 409 不删除已有对象；检查后被同名替换的资源不删除；删除超时保留未知责任；UID 确定的本轮孤儿可回收；404 保持幂等。

### F03 · 任务依赖缺少“成果进入下一任务”的合同

**位置：** `git-workspace.ts:110–155`；`host/dispatch.ts:219–227,430–445`。

`plan()` 无论节点依赖什么，都从 `refs/remotes/<remote>/<defaultBranch>` 获取 baseCommit。前序任务的成功 commit 只在收口时统一集成，没有由 Host 自动成为依赖任务的输入。DAG 目前确保 A 完成后才能启动 B，但不能保证 B 工作目录里存在 A 的代码。

R11 建立前序任务 A 的成功提交，其中新增 API 文件；main 未改变。依赖 A 的 B 已 ready，但创建出的工作树仍是旧 main，A 的文件不存在。这不意味着所有依赖都应合并代码：有些只是顺序依赖，但目前没有表达这种区别。

**建议：** 区分 `order-only`、`artifact-input`、`code-input` 等依赖类型。对需要代码输入的节点，在派发前由 Host 组合精确前序成功提交，产生不可变 execution baseline；若冲突，则阻塞在输入准备阶段，交给明确的集成任务处理，而不是让 Worker 自行猜测和 cherry-pick。保存 predecessorRunIds、inputCommits、artifactDigests、baselineCommit。

此改动要同步调整最终 task-set 的验证规则：一个后继提交可能已经包含前序提交，不能把它误判为重复/未知任务，也不能简单把所有分支再次机械合并。用依赖闭包与提交来源集合证明这次交付包含且只包含授权成果。

**验收：** A 建接口→B 调用接口时 B 能直接编译；A/C 并行→B 汇合可重放；冲突先于 Worker 执行暴露；A 重跑后 B 的旧输入显式标记过期。

### F04 · 当前 evidenceDigest 主要证明批准文本，不证明批准了哪一份成果

**位置：** `review-authorization.ts:21–31`；`index.ts:1012–1053,1094–1113,623–649,2698–2716`。

摘要包含 sessionId、needId、needRevision、kind、decision、note，没有包含计划内容、DAG、任务成功提交、验证证据或待交付集成提交。`createNode` 不推进 Need 修订，也不改变已有批准记录。R08 证明 closing 乃至 deployed 的 Need 仍可增加节点，批准摘要不变。

真正风险并不是“调研节点不该提前执行”。风险是：**用户批准的一个集合，可能在外部合并前已不是 Host 当时验证的同一个集合。** `closeGitNeed` 在多个 await 之前获取 nodes/taskRuns，缺少贯穿整个外部操作的交付快照/收口所有权。不能只在最终写事件前再做一次 CAS，因为外部合并已经发生。

**建议：** 每次批准绑定阶段特定的 ReviewSubject：需求内容版本、计划/DAG 摘要、输入成果摘要、scope policy、验证配置版本；verification 批准再绑定成功任务集合、对应 commit 和集成结果。人看到的是摘要对应的可读差异，不是只有一串 hash。

保持“ready 即可认领”的既定边界。把 freeze 放在本次交付尝试的快照上；新增调研/补充任务仍可创建，但必须属于新的计划修订或后续交付批次，不能悄悄进入旧批准覆盖范围。物质性变化使相应批准失效，而不是全局封禁前期节点。

**验收：** 批准后增删任务、替换成功 Run、改验证配置、改变集成 commit 均要求重新确认；外部合并期间无法用旧操作身份合并变更后的集合；同一批准不能被换对象重放。

### F05 · 验证集成提交，却可能记录另一个未经验证的默认分支提交

**位置：** `index.ts:684–746`；`git-workspace.ts:446–467`。

收口在 prepareClosing 阶段验证 integration。合并后 `verifyClosingMerged` 只 fetch 默认分支，并检查 integration 是默认分支最新提交的祖先；它没有验证最终 tree，也没有要求返回值等于 Gitea 报告的 mergeCommit。Host 把返回的最新 HEAD 写成 release.commit。

R05 先让 integration 通过真实登记命令，再让默认分支增加一个破坏测试的后续提交。`verifyClosingMerged` 仍返回这个失败提交；独立再次运行同一实际验证器会失败。问题不是 merge-base 错了，而是把“含有已验证祖先”当作“当前提交已验证”。

**建议：** 交付身份锁定到精确的 Gitea merge SHA，获取该提交并在独立验证目录复验；release 记录被复验的这个 SHA，而不是当时默认分支最新 tip。默认分支后续前进不应把其他变更吸收到本次 release。保留祖先关系检查作为额外证明，而不是验证替代物。

**验收：** integration 已通过但精确 merge tree 失败时拒绝完成；PR 合并后 main 再前进时，本次交付不错误绑定后续提交；Git 查询与 Gitea 返回互相印证。

### F06 · 收口的两个事件之间存在可复现恢复断点

**位置：** `index.ts:734–746`；`domain.ts:563–570`；`host/cleanup.ts:90–96`。

顺序是先 `release-recorded`，再 `phase-transitioned`。如果前者已成功落账、后者尚未完成时中断，Need 仍是 closing。正常重试重新生成 release，recordedAt 为新时间；而投影正确禁止已记录 release 发生任何变化，因此在推进阶段前就报错。

R07 在这个精确窗口注入中断，然后重试，得到 `release ... changed after recording`，Need 仍 closing。对照 C02 证明完全相同的 release 重放是幂等的，故根因在重试重新构造了不同结果，而不是投影普遍不支持重放。

同时 requiresRelease 清理门禁只要求 release 存在；在这个断点后恢复清理可能删除后续重试仍打算核验的 task refs，进一步增加恢复难度。

**建议：** 优先引入一次 finalization 事实事件，将已验证 release 与 Need 终态作为同一事实投影；若暂不变更事件格式，重试必须先读取并复用已存在的精确 release，再推进缺失阶段，不能再次生成 recordedAt。为 closing 操作分配稳定 operationId，清理门禁绑定 finalized 状态。多投影可由同一事件更新，不需要另建第二套 Run 数据库。

**验收：** 在每次外部 API 成功返回、每次事件 append 前后、每次 cleanup 前后注入失败/重启，都能得到唯一 release，或者显式等待人工处理，不会自动重复合并或永久卡在普通重试。

### F07 · 本地 Git 路径绕过了已存在的统一准入机制

**位置：** `host/dispatch.ts:175–389` 对比 `414–446`；`execution-capacity.ts:29–68`。

K3s 路径会排队、获取 capacity、重核配置、claim 并 finally 释放。本地 Git 路径直接 plan→claim→materialize→executeClaimed，没有 acquireExecutionOrCancel / executionCapacity 调用。R04 将调度器设为必定拒绝（模拟恢复盘点屏障），本地 Git 仍 claim 和执行，准入调用次数为 0。对照 C03 证明统一调度器本身确实尊重屏障。

**建议：** 将所有 Worker 入口统一为 `admit → freeze inputs → claim → execute → verify → settle → release`。本地 Worker 可以不需要 K3s pool，但仍需明确定义 workspace 并发、本地资源预算和恢复准入。把 provider-specific 行为放进 driver，不要每个派发函数复制一条调度链。

在第一次 await 后到 claim 前同时复查取消、workspace/config 版本和操作身份。资源释放由幂等 handle 管理，所有失败分支共享处理。

**验收：** local/K3s 同时请求同一限制时均遵守；启动盘点不只挡 K3s；取消排队不 claim；缩容恢复不会把已有占用丢失。

### F08 · 临时运行秘密的内存责任没有在全部终态释放

**位置：** `k3s-worker.ts:162,284–325,340–458`；成功删除 Map 项在 `459`。

plan 向 pendingRuntimeSecrets 放入原始 nonce/token；成功走过资源绑定后才删除。创建失败、计划后取消或准入失败没有统一 release/discard。R10 证明创建失败后 Map 仍保留该运行秘密。

它们不是模型 API key，但属于敏感运行能力材料；长期 Host 中失败积累同时扩大敏感材料驻留和内存占用。

**建议：** 用一次性、可 dispose 的 PreparedRun 交接秘密，消费即移交责任；成功、失败、取消、超时、丢弃准备对象都有终态释放。把准备尽可能移到实际准入后；无法避免时设置 bounded TTL 和容量，并禁止进入错误日志。不要将原始秘密加入 Session 事件以便“恢复”。

**验收：** 所有创建阶段失败、等待取消、绑定失败后 Map 回到基线；循环数千次不增长；无法重用旧准备凭据执行新 Run。

## 5. 有证据的设计取舍与静态审查项

### D01 · 全局 FIFO 的队首阻塞是已记录的设计，不是误实现

`execution-capacity.ts:112–157` 只考察 queue[0]。R09 证明 pool A 饱和会使后续 pool B 空闲任务也等待。实施文档 §15-A6 明确把“不允许 B 跨越 A”作为既有合同，本报告不将它计入缺陷。

取舍是全局严格到达顺序优先于资源利用率。只有当跨池吞吐成为目标时，再由用户显式选择“每资源域 FIFO + 跨域公平轮转 + 等待老化”；保留 strict-global 模式。不能打着性能优化旗号静默改公平合同。

### A01 · 官方 DSH 兼容性已进入新一轮变更窗口

截至本次查询，官方 GitHub 发布列表最新为 **2026-09-09 的 v0.1.5-alpha.2**。发布说明涉及 Session V3、Web 插件面板 API；前一版说明还涉及 Agent API/Inbox 调整。这里核实的是 GitHub release，不是 npm 默认 dist-tag。

当前包 peerDependencies 大量停留在 `0.1.2-alpha.1`；文档的官方发行版验证记录主要为 9 月 6 日；预设仍使用旧 persona 配置形态。不能沿用旧记录断言最新版一定可用，也不能反过来断言最新版仍缺 externalEventProducers。

根目录 package.json 开发依赖引用两个相邻开发工作树；vitest.e2e.config.ts 直接导入相邻 fork 的 decorator plugin。开发调试可以这样做，但独立可复现构建与官方装配证据不能依赖某位开发者电脑上的目录状态。

建议把兼容性拆成显式矩阵：DSH 版本/commit、Session 格式、事件生产者能力、批准审计能力、Subagent cwd/角色语义、Remote/面板 slot、安装/启动/卸载/重启。固定受支持组合；能力不满足只读展示诊断，不能伪装正常。开发 fork 继续仅是 fixture，生产不绕过官方约束。

### A02 · 租约、运行时限和用户取消是三个不同的时间合同

`k3s-worker.ts:291` 将 activeDeadlineSeconds 设为 leaseDurationMs/1000；Host 又周期续租。续租只更新 Host 租约，不延长 Job 的 activeDeadlineSeconds。因此健康长任务也可能在最初时限被 K3s 终止。把 ownershipLease、maxWallClock、heartbeatStall、API requestDeadline 分开。

`git-workspace.ts:729–742` 与 workspace-project.ts 的 Git exec 没有统一 timeout/AbortSignal；登记验证有 timeout，但派发取消未贯通到验证进程。给 Git fetch/push/clone、验证、结果采集、清理分配独立且有界的操作时间。取消应区分“停止观察”“停止任务”“保留成果”“清理资源”，不能统一等价删除。

这是源码可见的行为；本次没有在真实集群制造长时任务超时。

### A03 · 命令被批准，不等于测试实现不可被改弱

当前授权校验精确到 command/args/timeout/order，这是必要条件。可执行内容仍来自任务仓库：登记 `npm test` 并不阻止 Worker 修改 package.json 的 test 脚本或削弱断言。空验证配置也仍合法。

不要简单禁止修改测试；测试本来就可能随功能变化。建议建立两类证据：宿主控制的稳定验收基线/外部断言，以及任务新增/修改的项目测试。测试基础设施、构建脚本和安全配置的修改进入单独审查；空验证在 UI 和 release 中明确标识“没有执行自动验证”，不能统一显示 verified。针对不同任务类型配置最小必需验证策略，不能由模型临时降低。

### A04 · Gitea 保护分支上的真实协作没有闭环

`index.ts:662–664` 遇到 requiredApprovals>0 或非空 statusChecks 就拒绝自动收口。它没有绕过保护，这是安全的；但用户启用常见审核/CI 后，流程将停住。

建议 closing 操作支持 `pr-open → waiting-review / waiting-checks → mergeable → merged → verifying → finalized`，人工/CI 满足后按同一不可变 head commit 接续。不要为“全自动”而要求用户把保护规则关掉。

### A05 · failed/cancelled 的本地 Git 资源需要明确保留策略

本地 materialize 或 Worker/验证失败时，派发路径结算失败，没有像 K3s 那样为失败的本地 worktree/branch统一登记清理责任。并非所有失败目录都应删除：未提交代码可能有诊断和恢复价值。

建议给资源明确 `retained-for-review / cleanup-pending / cleaned` 状态、owner Run、磁盘体积和到期策略；保存未提交工作时提示用户，不 force 删除。即使保留，也要形成可发现、可审计的责任记录，而不是让它成为沉默残留。

### A06 · 前端存在“同一会话内的新旧请求竞争”和“跨工作区旧响应回填”风险

overlay 已使用 generation 和 AbortController，能保护跨会话/开关生命周期。但同一 generation 内多次 loadRuntime 没有请求序号，旧请求晚返回仍可能覆盖新状态；其刷新签名仅含 Run/cleanup 状态与 Need 数量，纯配置或外部池变化可能保持旧值。失败时保留旧值可以，但必须标为 stale，而不能当新鲜事实。

project-panel.tsx:110–153 的 refresh 与 gitSecrets effect 没有请求身份/取消检查。快速切换工作区或 cluster 时，旧响应可能回填新选择的候选项。Host 的保存校验降低越权写入风险，但体验和正确性仍需浏览器反序响应测试。

建议抽取带 requestSeq、AbortSignal、revision 和 lastSuccessfulAt 的资源查询 Hook；保存请求同时绑定起始 workspaceId/revision。补键盘焦点、Escape、焦点归还和 100+ 节点图的可读性测试。此项为静态发现，未作本次浏览器渲染实测。

### A07 · Worker 隔离建议做成可检查的能力档，而不是口头“安全容器”

源码已有 nonroot、drop capabilities、禁 privilege escalation、关闭服务账号 token 等基础措施。Job 当前固定 amd64，未显式设置 seccompProfile，资源限制主要是 CPU/内存。建议补 RuntimeDefault、临时磁盘预算、可写目录白名单与出网策略，先验证镜像和实际集群能支持，再宣称对应能力档。readOnlyRootFilesystem 不能直接加完就算完成，必须安排 HOME/TMP/workspace 的可写卷。

不要求本地工作树冒充沙箱；用 UI 明示“本机信任执行 / 容器受限执行”的不同保证。混合算力支持以 worker capabilities(platform/arch/resources) 实现，不把它扩成新的远程多租户平台。

### A08 · Worker 角色与 Orchestrator 角色应分别装配

同一 persona 开头声明 read-only orchestrator，后面又声明被委派时修改和提交；Agent policy 的 session-start 回调没有可见的 Worker 角色条件。是否继承到某个 Provider 的子代理取决于 DSH 装配，本次不能仅凭此断言继承缺陷。

但文档确有本地 Worker “produced no commit”的实测失败记录，角色/工具能力串扰应当列为排查假设之一，不应直接归因于模型能力。建议 Host 显式配置 orchestrator 与 worker capability profile，并在真实本地 Worker E2E 中证明：父会话不能写，子 Worker 能在指定 worktree 写/验证/commit，且不能改默认分支。模型自称“我是 Worker”不能成为授权依据。

### A09 · 状态文档应区分现状、历史过程、当前证据

实施状态同一文件包含“真实 Gitea/K3s 通过”的后段记录，也保留“真实环境尚未运行”等未刷新总结；顶部大量早期未完成结论后来已修复。代码行数、测试数量也随增量变化。评审不能把旧段落当当前漏洞。

建议保留原始日志不改历史，同时生成简明 CURRENT_STATUS：能力项、当前结论、源码 SHA、环境、执行命令、证据路径、已知失败、最后验证时间。`passed / failed / blocked / not-run` 四种状态分开。官方 DSH 兼容、真实本地 Worker、真实 K3s、真实 Gitea 不互相替代。

### A10 · 其他应安排但不应夸大为已证实事故的检查

`inspectWorkspaceGit` 直接返回 origin URL，应对已有 userinfo/token URL 做展示脱敏；有 token 的旧仓库不应把它传入 UI/模型快照。`boundedOutcome` 仅截断并不通用脱敏，须把已知秘密 redaction 与大小限制分离。

文件 write+rename 不等于断电持久化保证；按需要验证 fsync、父目录 fsync、截断日志、最后一条事件校验及备份恢复。Session 运行事件和 Workspace 配置分别有 owner，但跨域引用必须保存版本，不能“当前配置重解释旧运行”。旧 schema 迁移和缓存失效应有旧日志固定夹具。

这些事项本次主要为静态审查/设计建议，不计入 8 类已复现问题。

## 6. 推荐目标架构：本地模块化单体，不是微服务重构

建议继续以一个 DSH 插件交付，内部形成五个职责面。

### 6.1 DSH 适配面

只处理官方 Session/Event/Approval/Remote/Slot/Subagent API 与版本差异。业务不直接依赖散落在各处的 DSH 服务定位、事件布局和 UI slot 字符串。以实际能力探测选择适配器，不用吞异常 fallback 假装兼容。

### 6.2 工作流内核

纯函数决定命令是否合法、需要哪些事件、触发哪些副作用意图。核心对象为 Need、PlanRevision、NodeContract、Run、ReviewSubject、DeliveryAttempt。Worker/网络/React 不进入内核。

每条命令包含 commandId、expectedRevision、actor/authority、subjectDigest。live command 与 replay 共用可验证不变量，但要区分当前写入规则和历史事件迁移规则。

### 6.3 操作协调与副作用责任面

负责 scheduling、claim、输入冻结、执行、结果接收、closing、cleanup。关键改变不是加一个新数据库，而是把操作意图与外部效果的确认进入既有事件体系。

一个 Gitea merge 或 K3s create 不能靠“函数返回了”作为唯一完成事实。需要 operationId、resourceIdentity、request intent、observed outcome、next action。外部请求超时必须允许 unknown，不能被粗暴映射成 failed 或 succeeded。

对于本地单用户宿主，一次交付的串行协调/乐观版本检查足够起步；不必引入分布式锁平台。若允许多个 Host 同时写同一工作区，必须显式拒绝或增加持久 fencing，而不是假定单用户就一定单进程。

### 6.4 执行与证据适配面

LocalWorkerDriver、K3sWorkerDriver、GitDriver、GiteaDriver 通过窄接口执行。共同接收不可变 ExecutionInput，输出有身份的 Observation；只有协调器可判定业务 succeeded。

Harness 差异用 capabilities 表达：协议、cwd、非交互模式、commit 责任、取消语义、结果格式、平台/架构、版本范围。协议或能力不匹配时报错，不静默改模型、改 Harness 或用模拟结果替代。

### 6.5 只读视图与用户操作面

UI 默认展示“正在做什么、为什么等待、需要我决定什么、哪些结果有证据、哪些资源仍保留”。状态均来自对应事实域，显示版本与新鲜度。用户操作提交命令，不能在客户端自行推导 approved/verified/deployed。

### 6.6 关键对象建议

`NodeContract` 至少有目的、任务类型、受限写入范围、禁止路径、依赖类型与精确成果版本、验收标准、验证策略、预算、负责角色。它不是更长的自然语言 prompt；Host 可用它检查最终 diff 和证据。

`ReviewSubject` 按阶段选择需求内容摘要、计划摘要、任务集合、代码 commit、证据摘要、验证策略版本。批准文本用于可读解释，subjectDigest 用于绑定实际对象。

`DeliveryAttempt` 固定本次任务集合、integration commit、PR 身份、merge commit、验证证据和 cleanup obligations。多个 Need 并行执行可以，面向同一仓库的默认分支集成建议串行或显式排队。

`OperationRecord` 记录副作用状态：prepared、requested、observed、unknown、finalized。未知不是失败清理许可证；人可确认并接续，但不能伪造已经验证的事实。

### 6.7 推荐持续验证的不变量

1. 同一个 node 的有效 claim 只有一个；过期 claim 不能提交结果或删除新资源。
2. 同一 Run 的执行输入、provider、验证配置、代码基线不可换对象。
3. `succeeded` 需要任务类型要求的宿主证据，不能仅因模型 stopReason=completed。
4. 批准绑定的 subject 与执行/交付 subject 一致；物质性变化显式失效。
5. release 指向精确且验证过的 commit，不借用祖先关系替代。
6. 外部副作用有唯一持久责任；unknown 不自动变成 success。
7. 删除需要确定身份或 UID/hash 前置条件；不存在不等于查询失败。
8. 所有执行路径经过对应准入；重启盘点先于新工作。
9. UI 的旧缓存不可显示为新鲜已确认事实。
10. 来源、观察、推断分别标识，重放不能凭空制造外部执行证据。

## 7. 开发模式本身的优化，而不只是稳定性修复

### 7.1 让用户管理决定，不是管理所有线程

主界面建议分为任务概览、待决定项、异常恢复、证据抽屉。用户默认看一个需求的目标、当前阻塞、下一动作和可信结果；展开时再看 Worker、分支、日志、预算。并行数不是越高越好，应优先减少共享文件冲突与用户切换成本。

### 7.2 任务拆解以产物边界为中心

避免仅按“前端 Agent / 后端 Agent / 测试 Agent”拆分而没有接口约定。每个节点明确输入成果、输出产物和完成条件；先稳定接口/契约，再放行可独立实现的并行节点。纯信息搜集可以早运行；修改共享模块、迁移数据库、重写测试基线等进入明确风险策略。

### 7.3 交付状态不要混淆 merged 与 deployed

当前 closeGitNeed 只做 Git/Gitea 合并，却把阶段推进 deployed，并把 PR URL 存为 serviceUrl。若 deployed 在产品语义中只是开发交付，应明确文案或改用 delivered/merged；若意味着真实部署，需要独立部署 receipt、版本、环境和健康证据。不要为了名称去强行扩建部署平台。

### 7.4 不以模型评审替代确定性验证

多模型交叉质疑可提升发现问题的机会，但不能成为独立可信证明。保存结构化问题列表、源码位置、验证命令、复现结果和剩余不确定性。特别是不能由执行 Worker 自行修改验收规则后宣布通过。

### 7.5 为长期任务加入预算和可恢复的中间成果

分别限制 wall clock、模型调用次数/用量、自动重试次数、磁盘增长和用户打断策略。预算耗尽应进入 paused/needs-decision，而不是悄悄降级模型或无限重试。中间成果保存为可识别的草稿 artifact/commit，不把半成品混为 succeeded。

### 7.6 成效指标应围绕交付质量

建议观测需求到验证交付的总时长、首次验收通过率、返工节点数、合并冲突率、人工批准等待、取消收敛时延、重启恢复成功率、清理残留数和每次成功交付的资源消耗。没有基线就先记录，不给未测量的“效率提升百分比”。

## 8. 推进顺序与验收门槛

| 阶段 | 内容 | 必须拿到的证据 |
|---|---|---|
| 第一批：关闭信任与破坏边界 | F01/F02；统一凭据能力；精确补偿与 unknown 责任 | 非登记目标零带凭据请求；409/同名替换零误删；timeout 不清账 |
| 第二批：交付正确性 | F03/F04/F05/F06；任务输入、批准快照、精确 commit、收口幂等 | A→B 代码输入；批准后漂移拒绝；坏最终提交不完成；关键断点重放 |
| 第三批：执行统一与恢复 | F07/F08；lease/deadline；本地失败资源保留 | 本地/K3s 相同准入；取消无泄漏；重启先盘点；保留资源可发现 |
| 第四批：真实产品验收 | 官方 DSH 兼容；真实本地 Worker；Gitea protected PR；UI | 干净环境 install/start/stop/uninstall；真实提交和真实结果证据；无跳过发布门禁 |

前四批完成前，不建议优先增加更多 Harness、更多面板或新的远程企业功能。第五批可以增量穿插，但不要先做大拆分，再发现原行为已经复制错了。

## 9. 建议补入正式套件的测试矩阵

**故障注入：** 每个 create/replace/merge/push/delete 的请求前、服务端成功但客户端超时、响应后尚未 append、append 后尚未推进下一事件、清理前后。尤其覆盖“外部已成功、本地未知”的窗口。

**并发：** 同一 node 双 claim、同 Need 双 closing、不同 Need 同仓库收口、配置变更遇到排队、默认分支并发前进、相同 resource name 不同 UID、本地与 K3s 混合调度。

**成果链：** 单前序、并行多前序、冲突、前序重跑、纯顺序依赖、代码依赖、证据依赖、验证配置升级、任务重试导致旧证据过期。

**信任：** 未登记 endpoint+有效 ref、错误 repo、跨源 redirect、测试脚本弱化、禁止路径修改、旧批准换对象、Worker 伪造成功 JSON、有效哈希但不满足独立验证。

**兼容：** 官方受支持 DSH 的干净安装及原生批准、子代理角色、Session 恢复、插件重载、UI slot；本地开发 fork 的结果不替代这一列。

**用户体验：** 快速切换工作区、旧请求反序返回、保存时改变选中项、取消长操作、重开浮层、配置仅发生在另一窗口、stale 状态、键盘可操作。

## 10. 最终建议

PactFlow 的下一版本最有价值的定位，不是“能调用更多 Agent”，而是：

> **用户批准的那份任务，进入了确定的执行输入；Host 验证的那份结果，成为了确定的交付提交；任何中断，都能解释自己停在哪里、还欠什么责任。**

保留已有权限、CAS、清理和发布门禁基础。优先修复本报告的两项 P0 和五项 P1，再解决长期运行资源与体验；将全局 FIFO、早期调研准入、单机边界等既定选择作为显式合同，而不是以“重构”为名改掉。
