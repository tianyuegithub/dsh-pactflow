## 1. 保留的合同与本版不做的事

### 1.1 不变的架构和协作边界

正式 HOW、顺序和逐步合同仍归 `docs/development-plan-开发计划.md`；目标架构负责 WHY/终局 WHAT；实施状态只负责 WHERE-now 和验证证据。跨 Host、Agent、Client、Remote、Session Event、Worker Provider 的变更先进入正式计划，再实施。重构与行为修复分开验收。[S2 `AGENTS.md`；开发计划 §15.2–15.3]

仓库创建结果不明时，继续沿用“只读候选查询＋用户确认精确仓库编号”的既定半自动对账，不用 operationId 或名称匹配替代该确认。[S2 开发计划 §15.2:369]

## 3. 必须先写清的六组实施合同

### 3.1 批准、执行、交付分别绑定什么

不要用一个大 hash 承担所有职责，也不要让所有审批都依赖尚未产生的 commit。以下对象保存可回读的结构化内容，digest 只是内容完整性标识。

| 对象 | 最小绑定内容 | 约束 |
| --- | --- | --- |
| ReviewSubject | `schemaVersion`、评审种类、适用需求修订、该阶段相关内容摘要、授权作用域 | 需求审批不要求未来代码；计划审批不要求未来验证结果 |
| RunInputSnapshot | 节点/需求身份、执行 attempt、固定配置修订、基础 commit、各依赖类型与前序已接受成果、验证策略修订 | Worker 不自行换前序分支、输入基线或验收命令 |
| DeliveryManifest | 本次选中的节点与 Run、精确成果 commit、传递输入闭包、集成基线/候选、验证策略和批准引用 | 与仍可继续编辑的全局 DAG 分离，旧批准不能默默扩大交付集合 |
| ValidationReceipt | 实际验证的 commit/tree、验证策略及其实现摘要、环境/执行器身份、命令结果、工件摘要 | 与真正执行验证的对象绑定，不接受只有“passed”字符串的自报 |
| OperationRecord | 稳定 operationId、对象身份、授权引用、命令摘要、观察到的外部结果、恢复状态 | 不保存原始凭证；在请求发出前持久化意图 |
| Release/Finalization | operationId、manifestDigest、精确合并 SHA、该 SHA 的验证凭证、交付终态 | 清理责任单独保存，不以清理成功反推交付成功 |

**阶段性失效规则建议：**

| 改变 | 需要失效/重做的内容 |
| --- | --- |
| 需求语义、范围改变 | 相关需求/设计/计划与下游验收，按影响关系传播 |
| 选中任务、前序成果或验证实现改变 | 受影响的输入/交付 manifest 和相关验收批准；不无差别撤销所有历史评审 |
| 仅修改展示名称、非实质备注 | 依据明确的字段级规则判断，不能因全局 revision 变化就要求全部重新批准 |
| 新增不属于本次 manifest 的节点 | 不自动进入当前交付；维持 ready 即可认领，后续纳入交付时形成新修订/新批次 |
| 已完成 Need 的新工作 | 不复活旧终态；按正式合同进入后续 Need/交付批次，不能续写旧 release 的覆盖范围 |
| 凭据撤销、Provider 权限缩小 | 立即阻断受影响的新副作用；不可借“快照冻结”继续使用已撤销权限 |

实际字段归属、物质性判定和序列化规范必须版本化。集合排序、缺省字段、字符串规范化规则固定；不把凭据值或凭据值 hash 放入这些公开摘要。DAG 拓扑在最新 `graphRevision` 上原子检查，不能在两个请求分别通过旧图检查后形成环。Need 收口则使用稳定的 delivery/finalization 身份，不用一个跨整个系统的大锁代替所有不变量。

这些是对原 H6、H7、J4、J5 的合同细化，不收紧既定节点阶段准入。[S1 H6–H7、J4–J5；S2 开发计划 §15.2:370]

### 3.2 创建、授权、删除的身份链

**创建前的授权意图**记录：操作编号、Provider/集群身份、namespace 身份、资源种类、已选定的临时名称或受控分配规则、数量上限、允许动作、用途、清理范围和适用批准。新建对象此时不填写虚构 UID。

**创建后的回执**记录：服务端返回的精确 UID、相关版本、所属 operationId 和创建结果，并尽快持久化。后续自动删除从回执取得 UID 前置条件。删除用户既有对象则必须在授权对象中已有精确 UID 或 Git expectedCommit；不得把“允许创建临时对象”解释为“允许删除同名既有对象”。

Runner 必须在每个有外部副作用的入口校验真实授权引用、范围摘要和适用版本。手写 `authorization: granted`、环境变量开关或持有凭据均不能单独替代授权。没有业务需要的 branches/merges/cleanups 可以是空数组，但清单不能用空数组掩盖实际发生的动作。[S1 G2、G5、N2；S2 开发计划 §15.3]

**资源生命周期规则：**

| 观察结果 | 允许行为 |
| --- | --- |
| 创建成功且 UID 已确认 | 纳入本操作已确认资源清单；对该 UID 执行获准的生命周期操作 |
| 创建返回 409 | 409 本身不证明归属，不因本次失败去删同名对象。若是恢复重试，只有此前已持久化的同操作、同 UID 证据才能单独授权后续动作 |
| 创建超时/响应丢失 | 记录 `create-outcome-unknown`；不能假定未创建，也不能单凭 label/名称自动认领 |
| UID 已返回但落账失败 | 利用仍在内存的确切 UID 尝试有界补偿；重启后没有可靠回执时仍按未知责任处理，不臆造身份 |
| 删除已接受、对象仍在 terminating | 记录 `delete-requested`；不能视为清理完成 |
| 确切已拥有 UID 的对象已消失 | 可以确认该对象消失，但还须核对相关子资源责任 |
| 读到同名不同 UID | 不删除替代对象；单独记录旧 UID 已不在该名称上，其他责任继续核对 |
| 删除超时、403、连接错误 | 保留责任、原因和下次对账条件；不能当作 404 |
| 创建结果未定时暂时读到 404 | 不能据一次 404 清除创建意图；须覆盖迟到创建窗口或保留显式 unknown |

Kubernetes 对有 finalizer 的对象可先返回 HTTP 202，实际删除稍后完成；因此本方案将“删除请求被接受”和“指定对象已消失”分开。[W2]

最小集群身份校验（原 J1）随 H2 同批：kubeconfig 路径不是集群身份。绑定已授权的服务端/信任信息与 namespace UID 等可验证标识；不声称 Kubernetes 一定提供通用的全局 cluster UID。证书轮换或 namespace 重建应进入显式重核流程，不能静默把旧清理责任转交新环境。

### 3.3 DAG 成果输入与收口任务集合必须一起改

保留三类边：`order-only` 只约束顺序，`artifact-input` 注入精确文档/证据版本，`code-input` 注入已接受代码成果。历史边没有类型时，不能猜测它原来就表示代码输入；采用版本化迁移/显式确认，运行中任务仍绑定原输入快照。

代码输入的实施要求：固定基础提交、选中的前序 Run 和成果提交；按确定的拓扑顺序与稳定 tie-break 组合；记录实际得到的 baselineCommit/tree。重试尽量复用已保存的基线对象，不用新的 Git 时间戳重新合成后声称是同一 SHA。冲突在 Worker 施工前变成可解释的输入准备失败。

**特别注意传递依赖：** B 基于 A 开发时，B 的历史可能已经含 A。后续 closing 不能继续未经验证地假定“所有任务都是从 main 独立分叉、每个任务恰对应一个独立 merge parent”。需要联合测试 `verifyTaskSet()`、集成顺序、前序祖先去重与受准入约束的变更集合。ZIP 中该函数使用 `--first-parent` 和预期提交集合核验，这是 H7 的真实影响面，不是可以忽略的独立后续优化。[S2 `git-workspace.ts:416–441`；本轮设计推断，未运行新反例]

A 产生新成果后，不改写 B 曾基于 A-v1 成功的历史事实；应把 B-v1 对新交付标为输入过期，并要求重新验证/重跑或显式采用旧版本交付。拒绝不在批准闭包内的额外祖先变更，不能只证明“包含 A”就接受连带的未授权代码。

### 3.4 准入、快照、取消和资源释放

保留入队配置不可变及严格 FIFO：

```text
读取并固定非密钥配置/输入候选 → 入队 → FIFO 准入
→ 再核对取消、授权、操作身份及快照有效性
→ 完成 RunInputSnapshot → claim → execute → verify → settle
→ 幂等释放本地 handle，并对外部占用完成结算或保留待对账占用
```

“准入后冻结”不得实现成“排队结束后自动使用最新版 Settings”。原计划要求排队运行不因热更更换资源；版本失效时显式拒绝、取消或按获准流程重新入队，不能偷换配置。[S2 开发计划 §7.2:217–219；S1 H3]

本地 Git 与 K3s 共用恢复屏障和取消合同，但分别记实际资源额度。**释放进程内 permit 不等于已证明外部 Worker 停止。** 远端结果未知且可能仍占用容量时，应保留可恢复占用，不得用一次 finally 释放制造超配。范围化隔离也不得暗中允许 FIFO 越过队首。

分开 ownership lease、最大运行时间、心跳停滞时间、API 超时、清理期限。续租不默认延长 Job 的 deadline；取消等待不 claim，取消执行需保留终止/对账责任。PreparedRun 释放内存秘密与撤销已发出的令牌是两件事，都须按各自能力验收。[FULL:A02；S1 H3、H8]

### 3.5 精确交付与可恢复收口

H4 锁定精确 merge SHA 的方向保留，但要写出整个状态链：

```text
prepared → merge-requested → merged-observed → exact-sha-validated → finalized
                        ↘ outcome-unknown
                                           ↘ merged-validation-failed
```

这些名称首先是建议的内部操作状态，不直接替换 Need 领域枚举。

准备时保存 operationId、批准引用、manifestDigest、集成候选、目标分支预期基线、所用 merge policy 和清理责任。发起合并前复核当前 PR/repo/head/权限及批准对象；合并结果不明先查询确切 PR，不盲目再次合并。Gitea 返回的 merge SHA 必须与该操作对应，并在独立、受控目录中复验该提交。

finalization 应满足：

```text
release.commit == observedMergeCommit == finalValidation.commit
release.manifestDigest == approvedDeliveryManifestDigest
finalValidation.profileDigest == approvedValidationProfileDigest
```

`integrationCommit` 不要求与 merge commit 相等，它们是不同阶段的对象；祖先核验作为额外证明，不能代替精确提交的验证。

**合并后复验失败时，主分支可能已经改变。** 必须保存真实 merge SHA，禁止形成成功 release，不自动强推回滚；后续修复或 revert 由独立授权操作处理。后置复验只能保证“未验证成功就不宣告交付”，不能单独保证“任何未经验证的代码永不进入 main”。更强承诺须验证目标 Gitea 的原子条件更新/受保护校验能力，不能靠客户端合并前再 GET 一次就宣称没有竞态。

一次 finalization 事实事件可以避免本地 release/phase 两事件裂缝，但不能把外部 Gitea、Session 存储和 K3s 变成一个事务。采用稳定操作 ID、幂等投影、明确的持久化确认与外部对账。若暂不引入新事件，则复用既有 release 的 commit/时间/身份后补齐阶段；禁止重试时重建 `recordedAt`。

事件类型/producer 变更必须先验证支持的官方 DSH 写入与旧数据恢复能力。既有允许的“已交付 + cleanup-pending”保留：交付事实不因清理失败抹除，但完整验收仍不能把残留写成零。[S1 H4–H5；S2 开发计划 §14.2、§14.4]

### 3.6 验收必须分层，而不是统一看 exit 0

| 层次 | 回答的问题 | 典型值 |
| --- | --- | --- |
| 测试 verdict | 该测试的预期行为是否被观察到 | passed / failed / not-run / blocked |
| 操作 outcome | 业务/外部操作实际发生了什么 | succeeded / rejected / failed / unknown |
| 清理状态 | 本批责任是否已收尾 | complete / pending / unknown |
| 证据状态 | 报告、身份、工件是否齐全可信 | complete / incomplete / invalid |
| 范围门禁 | 此验收 profile 是否满足 | passed / failed / blocked |

例如，“创建超时后必须保留 unknown 账本”的负例，观察到正确 unknown 行为时测试可以 passed；不能因为报告出现 `unknown` 单词就拒绝该测试。反过来，测试 passed 不代表真实资源已清理完；完整 K3s 验收仍须完成或显式阻断清理门禁。

每次执行前固定 AcceptanceProfile（必需 suite、target、能力、清理要求及版本）。本地纯单测不必伪造 K3s ZeroProof；但完整目标验收不能把必需真实套件临时改成 not-applicable。not-applicable 只能来自事先固定的适用性规则，并输出依据；not-run/skipped/blocked 不折算为通过。显式 skeleton 也不能删掉后让总测试数下降来“达标”。

证据应同时绑定 source snapshot、产物 tarball、DSH/运行环境、suite/scenario/attempt、批准与运行身份。相同 target 的多个 attempt 保留历史，按固定策略形成最终结论；禁止不带 attempt 身份覆盖失败或把别的批次报告混进本批。文件 hash 只能证明内容一致，不能证明内容真实；Host 控制的 runner/采集器应与 Worker 可写目录分离，报告入库前防路径逃逸、软链接替换并再次核验摘要。

## 4. 修订后的工作包与实施顺序

### 4.1 第 0 批：只做最小验收护栏，不等待整套基建

目标：先使后续修复不会“无证据过关”，但不让 TTL、TestSuiteSpec 等较大任务拖住 P0。保留唯一写入方串行实施；这里的优先排序不是增加多个并行写入者。

| 工作项 | 最小内容 | 退出标准 |
| --- | --- | --- |
| G0-min（新增编排项） | 固定输入来源、命名空间、当前 `HEAD/dirty/files` 和拟修范围；将本版获准合同并入计划 | 能区分历史复现、当前静态证据、新测试及未知项 |
| G1-min | 为本次 P0/P1 负例建立最小明确门禁；required 集合不因环境未就绪而缩小 | 错版本、缺报告、失败、零执行均不会标为该范围通过 |
| G4-min | 保存成功/失败原始报告与命令摘要；失败不在 finally 删除唯一证据 | 可回看本次负例与对照，不依赖终端滚屏 |
| G6-inventory | 将四份骨架、其他必需 suite 及其真实环境要求列为显式未完成 | 仍如实失败/未运行，不删断言、不计覆盖 |
| C-min | 记录支持基线和候选，核对新事件/批准/子代理等必要官方能力 | 兼容未知保持 unknown；不阻止可隔离的安全修复，也不冒充已完成安装 |

**第 0 批不要求先执行真实 K3s，不要求实现 G1–G6 的全部功能。** 这些最小护栏就绪后立即进入 H1/H2。

### 4.2 第 1 批：H1/H2 的安全修复与对应负例

| ID / 来源 | 必须交付的最小修复 | 依赖与分类 | 主要验收 |
| --- | --- | --- | --- |
| H1 / FULL:F01 | Agent 只选登记 Provider 与仓库；Host 绑定 endpoint、认证方式、credentialRef、允许仓库及配置修订 | 合同冻结后 A；真实 Provider 路径 B；旧绑定迁移随本项 | 未授权端点/仓库/重定向收到的带凭据请求数为 0；合法路径仍通过 |
| H2 / FULL:F02 + SCRIPT:R07 | 持久意图与 UID 回执；仅确认归属的对象可删除；超时保留 unknown；DELETE accepted 后继续核实 | G2 的两阶段身份合同、J1-min、J5-min；A 实现+B 实测 | 409/同名替换不误删，删除受理不冒充删除完成，迟到创建/崩溃不丢账 |
| H8-min | 与 H2 失败路径直接相邻的内存引用释放修复 | 同模块小变更可同批，但单列回归；A | 创建失败后敏感临时映射不持续增长；不得为“释放”删除身份不明资源 |

**H1 补充边界：** Provider 的配置必须由可信用户路径拥有，不能让 Agent 先修改登记配置再借 providerId 绕过约束。HTTPS 默认；有意允许的本地 HTTP 例外应精确到环境和端点，不能泛化成任意内网地址。历史不合规端点保留待确认/阻断状态，不静默改协议。

Git remote 与 API baseURL 的匹配应识别登记的 SSH/HTTPS 地址映射、API 子路径、端口和仓库身份，不能简单要求 URL 字符串相同，也不能只看 hostname。受权 API 默认不跟随重定向；确有需要时逐跳核验允许来源和路径。Gitea API 与 Git fetch/push 的认证链都要纳入检查，避免只堵绑定工具而遗漏其他携凭据出口。[S1 H1；v2 补充建议]

**H2 补充边界：** 无 ownerReference 不等于无已确认 UID；有 label 也不等于拥有删除权。账本损坏或存储不可写时，不得先创建再补写；只阻断相应不变量的范围，不扩大删除，也不偷偷改 FIFO。已知密钥的输出前脱敏（J2 的必要部分）随涉及的日志路径修改一并落地。

### 4.3 第 2 批：按合同依赖修复交付链

本批顺序采用“共享合同 → 输入与批准 → 统一执行 → 精确收口”，不机械沿用 H3、H4、H5、H6、H7 数字顺序。独立且不改变最终合同的最小幂等补丁可以提前，但整条交付链联合验收前不得宣称全部闭环。

| 顺序 | ID | 实施内容 | 进入条件与退出标准 |
| --- | --- | --- | --- |
| 2.1 | J4-min + J5-min | 明确 graph/Need/operation 的原子边界；稳定操作身份、版本化共享对象及恢复语义 | 跨进程相反加边不能成环；同 operation 重试不产生新身份；依赖官方能力的字段先核实 |
| 2.2 | H6 / FULL:F04 | 阶段特定 ReviewSubject；固定 DeliveryManifest；可解释的实质变更失效规则 | 未变化对象不反复审批；选中任务/验证/成果变化拒绝旧批准；新非交付节点不被强行阶段阻塞 |
| 2.3 | H7 / FULL:F03 | 三类依赖、精确前序成果、确定组合基线、传递闭包与冲突处理 | A→B、A/C→B、A→B→C；前序重跑失效；closing 不因前序已在后序历史而漏算/多算 |
| 2.4 | H3 / FULL:F07 | 本地/K3s 共用恢复准入、配置快照、claim、取消与结算 | 排队取消不 claim；权限撤销不继续发副作用；外部仍运行时容量不被当作已释放 |
| 2.5 | H4 / FULL:F05 + J12-min | 合并前检查候选与目标，合并后精确 SHA 独立复验；固定验证策略及实现 | main 前进不误绑 release；坏 merge SHA 不形成成功；测试实现被改弱不能无提示继承旧批准 |
| 2.6 | H5 / FULL:F06 | 稳定 finalization；优先单事实更新投影，否则兼容地复用已记 release 补齐阶段 | 各外部返回/append/重启边界可恢复到唯一交付或显式阻断；普通重试不因新时间撞自身 |

**验收方式：** 每项先新增或纳入可证伪的失败用例，最小修复后在原条件下通过，再执行与前后项的组合回归。不得用“新代码必须有新默认参数，因此旧反例不算”规避原风险；确有协议迁移时同时测试旧输入的明确拒绝/迁移行为。

### 4.4 第 3 批：补齐验收工程与真实运行准备

| ID | 内容 | 验收要求 |
| --- | --- | --- |
| G1 完整版 | 版本化 AcceptanceProfile、TestSuiteSpec 与范围门禁；保留全部 attempt 历史 | 缺工件、错 hash、旧源码、重复身份、跳过必需项、伪造 passed 均拒绝；合法负例可 passed |

| G6 | 实现四份骨架；未就绪前显式 required-but-not-run / failed | 实现前总门禁不得绿；启用后验证真实动作与断言，不以 `expect(true)` 或减少发现数代替 |
| H8 完整版 | PreparedRun 一次性消费、dispose 与故障/取消/丢弃路径；容量和期限控制 | 多轮循环不积累引用；过期准备不能用于新 attempt；区分引用释放与远端凭据撤销 |
| B1-prep + J11–J14-min | 诊断包、时限、失败 worktree 责任与父子能力装配的隔离验证 | 真实运行前已能定位 Run/child/commit，且失败现场保留在授权边界内 |

G3 的 TTL 样本与主动清理样本分开；TTL 观察超时后可以按 UID 主动收尾，但其 TTL verdict 仍为 failed/blocked，不能变成 passed。TTL-after-finished 从 Job 完成/失败状态计时，且会等待生命周期条件；它不证明未绑定 Secret 已清理，也不是活跃 Worker 的执行时限。[W3]

CURRENT_STATUS 是可再生成的只读视图，不成为第二份计划或业务事实源。测试工件、Session 事件、临时账本按各自事实归属保存；禁止为了“统一”再造一套运行数据库。

下列项目在真实动作前须核对影响清单、明确的授权引用及适用范围。只生成方案或完善脚本不构成执行授权。

| B2 | K3s 创建/清理负例、TTL、探针账本、真实进程跨重启 | 精确 UID、集群身份、每步意图/回执、崩溃位置、恢复行为；故障后仍可发现责任 |

| C 兼容线 | 未修改官方 DSH 的安装、启动、面板/Remote、子代理、恢复、卸载；旧数据升级 | exact version/commit、包来源、artifact hash、命令、报告、阻断原因；同包重装与跨版本升级分开 |

B1 的 RunDiagnosticBundle 采用白名单内容：项目/父子会话身份、run/attempt、非密钥输入/授权引用、相对 cwd、基线/HEAD、受限变更摘要、结构化工具调用摘要、可获取的 stop/exit/cancel/deadline、脱敏日志。不能无条件导出整个环境、prompt、thinking 或 patch；确需完整源码差异时使用受限工件并单独核查秘密。模型未返回 stopReason 时写 unknown，不伪造。

B1 先验收“有真实代码提交”的原目标；不通过把代码任务改成“允许 no-op 的调研任务”让旧失败变绿。父编排器只读、子 Worker 在指定 worktree 可写的角色边界须通过实际装配证明，而不是仅靠提示词自称身份。

| J13（新增） | failed/cancelled 的 worktree、分支、诊断的保留期限、容量、归属和回收责任；保留不等于泄漏，删除不丢用户变更。最小部分随 B1，来源 FULL:A05 |
| J14（新增） | 编排器与 Worker 的角色/工具/cwd 能力隔离，避免子 Worker 继承父侧只读限制；最终靠真实子代理验证，来源 FULL:A08 |

H8 的 Map 回基线只能证明临时引用已释放，不等于 JavaScript 字符串内存已物理擦除；远端令牌是否可撤销、何时失效单独记录。不得夸大这项内存治理的安全保证。

## 5. 官方 DSH 兼容与旧数据迁移

### 5.1 更新“最新”事实，但不自动升级支持基线

原方案记录 `v0.1.5-alpha.2`。截至本轮 2026-09-10 查询，官方 GitHub 发布列表顶部已有当天发布的 **`v0.1.5-rc.1`**，tag 为 `dsh-v0.1.5-rc.1`，页面显示提交 `183f08e`。这是官方 release/pre-release 证据，**不是 npm 默认 dist-tag 或本插件已经兼容的证明**。[S1 C 类；W1]

将版本分为“最后实证通过的支持基线”和“待核查候选”，候选新发布不自动触发生产升级，也不无限追新拖延当前修复。每轮正式验证冻结一个具体版本；新版本进入单独候选记录。

| 能力 | 需记录/验证的内容 |
| --- | --- |
| 官方装配 | Node、DSH 版本/commit、来源、插件 tarball SHA、peer 与实际安装依赖 |
| Session/事件 | 格式、producer 声明、append/持久化保证、新事实事件是否允许、旧日志读取/续写 |
| Approval | 原生审计、一次性批准、摘要与对象版本、消费后崩溃恢复 |
| Subagent | 指定 cwd、角色与工具隔离、父子 Session 关联、取消与续接 |
| Web/Remote | 注册、面板 API、投影刷新、旧响应处理、卸载后入口消失 |
| 生命周期 | 冷启动、重启盘点、锁/账本恢复、插件卸载和受控升级 |

结果细分为 `verified / not-tested / plugin-incompatible / upstream-capability-missing / blocked-environment`。分类含义保留原计划：C 项的后续处置由真实能力检查决定；不能因为测试没跑就结论“必须等上游”。若能力确实缺失，给出最小必要上游契约；生产不回退开发 fork。

### 5.2 迁移不是等最后安装时才考虑

H1 配置绑定、H6 批准摘要、H7 边类型/输入、H5 事件与 release 的变更均有旧数据影响，应随该项定义迁移，而不是全部留到最后。

| 历史数据 | 安全迁移合同 |
| --- | --- |
| 手工 endpoint + credentialRef | 唯一、可信 Provider 匹配并经适用确认后再激活；不把历史字符串自动升级为有效授权 |
| 旧批准摘要 | 可展示旧审计，但不自动赋予新版 ReviewSubject 的批准效力 |
| 无依赖类型的 DAG | 保留历史语义；新交付显式分类。运行中任务不被热改输入 |
| 已有 release、阶段未推进 | 精确核对并复用原 release，恢复缺失步骤；不得重建 recordedAt 或重复 merge |
| 无新字段的清理记录 | 不能凭空补 UID/cluster identity；保留只读证据与可操作阻断 |
| 旧 producer 不可续写 | 只读、受控迁移或明确阻断；不绕过官方事件规则 |

升级前排空或冻结到明确 checkpoint，保存与校验可恢复数据；旧版本只读/写入能力分别记录。不允许两个不兼容 writer 同时打开同一日志，也不假定新版写入过的数据可直接回滚给旧版续写。没有确定数据兼容方案时拒绝有破坏性的自动降级。

**ZeroProof 的边界：** 本批已确认资源以及未确认创建意图均纳入责任清单；不存在未解释的本批残留，才能给完整收尾通过。对非本批资源，以本执行器没有发出越权动作、隔离环境中的 sentinel 对照和精确身份记录证明边界，不承诺在多人共用环境中“所有外部对象在整个测试期间绝对没被别人修改”。

**正常对照至少包括：** 合法绑定、合法 UID 删除、正常 FIFO 派发、合法内容批准、依赖代码成功进入后序、精确合并提交验证通过、普通重试恢复、完整证据门禁通过。禁止通过禁用全部功能或把全部结果判 unknown 达标。

## 7. 分层收口门槛与状态报告

### 7.1 三种结论必须分别报告

| 结论 | 允许宣称的范围 | 不得偷换成什么 |
| --- | --- | --- |
| 单项修复完成 | 固定源码和条件下的失败复现、最小修复、对照回归完成；未覆盖边界显式列出 | 不等于真实集群/官方安装通过 |
| 真实路径验收通过 | 授权范围内某 Provider/环境/版本/场景的实际闭环有证据 | 不等于全部 Harness、全部环境或其他版本通过 |
| 本轮完整目标收口 | 冻结范围所有必需项均满足，适用 B/C/D 已闭环，同一产物链一致 | 不能把 not-run、blocked、unknown 或骨架折算为通过 |

每个实现收口点仍遵守原合同：`pnpm run check` 与 `git diff --check`；先失败后通过，不削弱断言和时限。环境缺少工具时记录 blocked，不伪造命令结果，也不把降低 Node/依赖要求当修复验收。[S2 开发计划 §15.3]

“同一产物”指对固定源码候选构建一次后，用同一个 tarball 做后续集成、安装验证；源码单测自身不是在 tarball 上执行，也必须记录它对应的源码摘要。修改源码形成新的候选和证据批次；不能要求所有开发提交共用一个旧 tarball。

### 7.2 建议的单项交接记录

```text
workItemId: H2
contractOwner: docs/development-plan-开发计划.md 的对应已批准章节
scope: 允许修改的模块/文件与禁止触及的边界
blockerClass: A 实现；B 真实验证
sourceIdentity: HEAD + dirty 状态 + relevant-files digest + lockfile digest
acceptanceProfile: 固定的 profile ID/revision
beforeEvidence: 原条件失败用例与报告
changeSummary: 最小修复以及被明确排除的扩大范围
checks: 实际命令、环境、结果、报告路径/摘要
artifactIdentity: 若有构建产物，记录 tarball digest
remainingBlockers: 未运行项、批准需求、unknown 责任
status: 单项完成 / 真实路径通过 / blocked；不使用模糊的“整体 done”
```

这是一种记录格式建议，不是新增一份计划文件。实施状态引用该证据记录；源码/运行事实优先，不能以计划勾选代替证据。

### 7.3 不以规则数量作为优化结果

在正确性达标后，优先记录真实需求从发起到可验收提交的耗时、人工介入次数、诊断定位时间、取消/重启后的恢复完成率、错误交付数和未解释残留数。它们是观测指标，不预设虚构基线，也不通过隐藏失败降低分母。成本/token 等新增指标在数据来源明确后增量加入。[FULL §7.6；v2 执行建议]
