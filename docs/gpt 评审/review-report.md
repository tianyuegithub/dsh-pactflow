## 一、结论

**方向值得继续，但当前材料不能支持“已经完整交付、已在官方 DSH 上可用”的结论。下一轮应从继续堆加固条目，切换到完成一条可复现、可解释、可恢复、可机器验收的真实开发闭环。**

PactFlow 最有价值的定位是“DSH 内的软件工程工作流控制面”：人决定目标与批准，Host 裁决状态和交付，Worker 提交候选成果，事件记录事实，界面呈现真实状态。多 Harness 和 K3s 应服务于这条闭环，而不成为单独的平台扩张目标。

现有设计并不缺少常见的工程概念。CAS、跨进程文件锁、租约、精确 Job 身份、清理账本、持久审批、验证配置和失败关闭都已经考虑。主要问题是：部分合同尚未被端到端证据证明；有些验证脚本之间的语义不一致；状态文档出现自相矛盾；若干跨边界的一致性与安全问题仍需细化。

## 二、应保留的设计

### 1. Host / Worker / Client 权限分离

Host 负责门禁、调度、验证与交付，Worker 不直接写 Session 状态，Client 不制造领域事实。这是产品可信性的基础，不能为了“更自主”让模型直接将任务或需求标记为交付成功。

### 2. 事件作为领域事实，投影可重建

根 Session 加绑定 Workspace 表示项目，不在 Settings 维护第二份项目注册表，避免多份业务状态互相覆盖。这里要保留“每类事实有唯一 Owner”的含义：Workspace 配置、凭证和外部资源仍有各自的权威来源，不应把所有配置强行塞进 Session Event。

### 3. 人工门禁、精确资源身份和失败关闭

文档明确验证配置不是操作系统沙箱；身份不明不得按可复用名称猜测删除；清理责任先持久化；远端创建结果不明采用用户确认精确资源编号。这些边界值得保留。

### 4. 不推翻已经裁决的三项决定

目标架构第 90–92 行已经明确：就绪节点允许提前执行调研；Gitea 结果不明采用半自动精确对账；远程企业平台为永久非目标。本次不建议将全部节点强制限制到计划批准后，不建议第二份项目数据库或中央服务，也不把已有的 Gitea 对账机制当作新增建议。

依据：`docs/architecture-目标架构.md:38–71, 90–92`。

### R01：当前不是可复现的评审/交付包

`package.json:30–78` 中 45 个 `link:` 依赖指向 `deepseek-harness-pactflow-p0` 与 `deepseek-harness-pactflow-upstream-pr` 两个相邻目录。`tsconfig.host.json:4–5` 引用缺失包与相邻 DSH；`vitest.e2e.config.ts:2` 直接引入相邻源码的测试插件。离线执行 `check-package.mjs` 立即因缺少 `packages/dsh-pactflow/package.json` 而失败。

这可以作为开发态接缝，但不能证明第三人在一台干净机器上得到同样结果，也不能证明最终 bundle 不依赖私有实现。后者必须检查实际产物。

建议区分 development 与 release 两条明确通道：开发态允许显式本地覆盖；发布态固定官方基线，禁止隐式 sibling links。交付材料包含完整插件源码和测试、来源 commit/dirty tree 摘要、工具链版本、产物摘要和真实报告。构建一次后测试、安装、发布同一个 tarball，不在最后一个步骤悄悄重新构建。

### R02：证据收集不等于验收通过

离线探针 P08 构造 5.1–5.7 七项证据，全部 `verdict=failed`，证据路径不存在，没有 zero-proof 文件。真实执行所附 `evidence-collect.mjs`，**退出码为 0**。P09 将其改成全部 `passed` 但 `conclusion=unknown`，仍为 0。

原因：`scripts/evidence-collect.mjs:38–53, 64–72` 只检查找到条目、结构及 target 齐全，不因 verdict 或 conclusion 拒绝，也不要求 ZeroProof 存在。

必须区分：收集失败证据本身成功是合理行为，因此不是要求 collector 永远把失败数据拒之门外；问题是它不能充当 acceptance gate。脚本中 “复用严格语义” 的注释会加剧误解。本次没有证明它已被用于对外发布假成功；`check:release` 走的是另一条门禁。

建议保留 `evidence:collect` 的采集语义，新增显式 `evidence:verify` / `acceptance:gate`。后者根据固定验收清单检查目标完整、结论为已验证事实、执行结果通过、工件存在且摘要匹配、源代码与运行环境版本一致、所需资源清理证据成立。任何人工批准的豁免应是可追溯独立状态，不能改写成 passed。

验收反例必须覆盖：全失败、unknown、缺工件、错误 hash、旧 commit、重复 target、缺 ZeroProof、零测试、跳过测试。

### R03：Schema 在该严的地方不严，在可选字段上又过严

`evidence-schema.mjs:23–28` 声称 blocking 可选，但通用 `hasExactlyKeys` 把它列成必填。P01 的普通 passed JSON 因缺 blocking 被拒绝；显式 undefined 只在内存成立，JSON 序列化会移除字段。

同文件第 53–70 行的 ZeroProof 只校验形状。P03 的空 before/after/cleaning 被接受，P04 的 after 仍有两个 Job 也被接受。结构校验允许这些输入本身未必错误，但不能据此宣称零残留。

`impact-list.schema.mjs:30–64` 要求 branches、merges、cleanups 都非空，使无合并、无清理的只读操作难以如实表达；cleanup 任意 kind 都能配 `precondition=name`，没有强制具体 expectedUID/expectedCommit。P05、P06 复现了这些行为。授权 pending 可以通过 draft schema 是正常的，不能据此断言执行器存在授权绕过；应另有执行准入验证。

建议采用资源类别区分的结构：K8s 操作携带不可混淆的集群身份、namespace、kind、name、expectedUID；Git 操作携带仓库身份、ref、expectedCommit；临时目录携带受控根路径与创建责任标识。名称可用于定位，不能替代删除前置身份。无操作允许空数组，必须字段不靠“占位字符串”满足。

ZeroProof 应证明“本批已确认拥有的资源已收尾，外部既有资源未受影响”，而不是“整个 namespace 被清空”。仅 0 Pod 不能证明 Job、ConfigMap、Secret、Git refs 与本地目录都已收尾。

### R04：K3s 批量验收尚未实现完整收尾

`run-real-k3s-batch.mjs:33–41` 两个导出函数直接抛出 not implemented；P10/P11 已离线复现。第 63–65 行按 suites→ttl→zero-proof 串行执行，前一步 throw 后后续不会执行，也没有统一 finally 收尾。

显式失败是优点，不是伪成功。但这条脚本当前不能完成它声称组织的整批闭环。即使未来填好占位函数，只补 happy path 仍不够。

建议：先持久化批次责任及资源意图；执行测试与独立 TTL 观察；无论主测试失败与否，均进入有界的清理/对账阶段；最后分别报告测试结论、清理结论与证据完整性。未知身份应保留责任并阻断自动删除，绝不能为了“归零”扩大删除范围。

TTL 测试与主动清理测试要分开：TTL-after-finished 仅在 Job Complete/Failed 后启动，到期使 Job 可被级联清理，并受 finalizer 等生命周期约束。手工删掉 Job 后看到空列表不证明 TTL 生效；TTL 也不是运行超时控制。[W3]

### R05：官方兼容、重装、升级应分别证明

`profile-runtime.mjs:9–15` 能避免悄悄回退 TypeScript 开发源，是正确修正；但任意 `.js` 路径均被分类 installed-cli，P07 已复现。主验证脚本会检查路径可读和版本字符串，因此本报告不将选择器没有存在性检查单独当漏洞；关键是两者都不等于官方来源证明。状态文档第 84 行也已经承认这一边界。

`verify-profile.mjs:34–42` 对同一个 tarball 再安装一次，验证的是重装幂等、Bundle 不重复，**不是跨版本升级**。状态文档第 155 行已经记载旧 0.1 producer 声明不能追加 0.3 事件：读旧日志与继续写旧项目是两件事。

建议使用兼容性矩阵：官方 DSH 包名/精确版本/来源摘要，插件版本及摘要，Node/OS，external event producer、Remote、subagent cwd 等所需能力。不能仅以路径或格式正确的版本号证明“官方”。截至本次查询，DSH 官方仍声明处于快速迭代的 developer preview，会出现破坏性兼容变更；这是持续维护合同，不是一次性验收。[W1]

升级验收必须带真实旧数据：旧版本建立含已批准评审、排队/运行任务、待清理责任的项目→停止→升级→回放→恢复→完成→检查批准不会错误复活、资源不重复创建。无法续写的历史项目必须在升级前给出只读、受控迁移或阻断策略，不得绕过官方事件注册边界。

### R06：优先打通本地真实 Worker，而不是继续用测试数量替代

`implementation-status-实施状态.md:202–203` 最新明确记录真实本地 Worker 两轮稳定失败，错误为 `PactFlow Worker produced no commit`，父侧 dispatch/spawn 已启动，但子代理现场无法取得。本次没有核心源与测试，不能独立定位根因，也不应直接相信“已归因子代理”足够完成诊断。

建议在公共可用边界建立 RunDiagnosticBundle：关联 rootSessionId/childSessionId、run/attempt、授权与输入快照、cwd、基线/HEAD/工作树差异、工具调用摘要、模型终止原因、deadline/cancel/exit 信息和最后受限日志。清理临时脚手架之前导出脱敏诊断；日志有时限和容量，不无限保留秘密。

代码任务无 commit 应继续失败关闭，不能为通过测试放宽。调研任务可以采用明确不同的成果合同，但这是任务类型设计，不是为当前失败补后门。

### R07：运行补偿的名称删除与 UID-only 合同冲突

目标架构第 61–62 行要求持久资源按 UID 删除、未确认身份不按可复用名称删除。状态文档第 172 行却记录“运行路径按逐运行名称补偿”，同时探针路径坚持未知身份保留责任。

这至少是文档层面的直接冲突；由于实现不在包内，不能把它断言为已证实的越权删除漏洞。应优先查所有运行/探针/超时/恢复清理入口，判断运行路径是否实际上取得了可信 UID 并带前置条件删除；若没有，必须统一失败关闭合同。

不能用“随机名称很独特”替代精确所有权。创建响应丢失后可能有重试、删除重建或另一进程介入。已知责任无法安全自动解析时，应保留账本、展示人工核验步骤，而不是用宽删除恢复可用性。

### R08：Host 端脱敏覆盖不到上游原始日志

状态文档第 187 行写明 HTTPError 响应体经容器日志回传后才由 Host 脱敏，第三方镜像脚本由日志读取后脱敏兜底。

Kubernetes 的容器运行时会接管 stdout/stderr，并提供节点日志/API 读取路径；因此 Host 的事后脱敏并不能移除此前可能已写入的原始日志。[W4] 这是边界推论，不代表本次已经发现泄漏的密钥。

对自己控制的脚本，在输出错误体前脱敏/摘要化；拒绝含 userinfo 的 baseURL 等容易隐藏凭证的配置形式；尽量按运行发放短时最小权限凭证；日志读取权限和保留期单独控制。对无法约束输出的第三方 Harness，明确可信级别与风险，不宣称“任意秘密从不入日志”。Host 再做脱敏仍有价值，但只能作为第二道防线。

### R09：多套真实测试入口的启动合同不一致

`run-real-web-gate.mjs:19–36, 51–58` 检查凭证文件内 Gitea token 是否存在，但不像专用 Gitea runner 那样把读取值注入子进程，也未检查模型 key；注入 K3s/Gitea flags，却未统一专用 `run-real-suite.mjs:7–19` 使用的 `DSH_REAL_CRASH` 与 `DSH_REAL_APPROVAL`。

测试源码缺失，因此无法断定具体哪些 suite 会跳过或内部自行读取凭证；可以确定的是入口的前置和环境合同不一致，且依赖外部进程环境。

建议声明式 TestSuiteSpec：套件 ID、所需凭证引用、能力、准入授权范围、环境标志、时限、预期报告、清理类别。专用 runner 与全集 runner 均从同一规格生成。只把最小必要环境传给对应子进程；“环境变量为 1”表示启用测试，不能代表用户已批准外部写入。

impact-list schema 目前没有被这些 runner 导入。应检查实际写入端的批准合同，不能仅要求 Agent 在文字里读过影响清单。

### R10：原始报告被删，当前状态没有唯一答案

`check-release.mjs:23–24` 与 `run-real-web-gate.mjs:62–63` 在 finally 删除测试报告目录。失败时也删，削弱复核能力。建议把通过/失败报告复制到持久验收目录，附源码摘要、产物摘要和工具链；临时 home/凭证依旧及时清理。

同一个状态文档第 196–201 行称决策已定且真实 Gitea/K3s 通过，第 204–205 行又称决策待定、真实验收未运行。不能挑一个更乐观的段落当事实。

建议把当前状态生成成单一有限表：能力→源码/产物版本→最新证据 ID→结论→未闭合项。旧过程进入按批次不可变历史报告。对失效、被后续失败替代、只适用旧版本的证据显式标记。

现有 `release-web-report.mjs` 有值得保留的严格检查：漏测、pending/todo、失败、重复 suite、断言数不一致会拒绝，P12–P14 做了正反例对照。改进不是推翻它，而是把“必须有哪些验收项”从当前目录扫描提升为版本化清单；否则删除测试文件也会缩小必测集。

### R11：配置变更需要由自己的事实源触发刷新

状态文档第 189–190 行明确：Workspace 从 R1 改成 R2 时浮层不感知，只有新增需求导致会话投影签名变化后才显示 R2；失败则保留旧值等待下次变化。

这是低耦合刷新合同未闭合：另一个项目改变池容量、Settings 独立编辑、本会话长期不动时，都不应依赖碰巧发生的需求变化来反映配置。

建议 Workspace revision、Pool capacity version、Settings revision 分别驱动 invalidation；响应携带 sourceVersion/asOf/stale；刷新失败应独立有界重试并显示旧值状态，不因无关事件不来而永久静默。

### R12：重构不应止于大文件搬家

状态文档第 175–181 行描述 `this.` 改成 `host.`、原方法保留薄代理、工厂让测试 Reflect.set 覆盖继续有效；index 从 3442 降至 2753 行，五模块共 1334 行。

这是合理的第一阶段保行为提取，不能据此说代码必然更差；但它本身不证明职责与依赖已经解耦。后续应让 cleanup 只依赖账本和删除端口，dispatch 只依赖调度/执行端口，recovery 只依赖读取/对账/恢复命令；纯 reducer 不接触 I/O；测试通过公开窄端口注入错误，不覆盖大宿主私有方法。

## 四、还应明确的架构合同

以下为架构差额建议，不等于断言实现不存在。部分基础机制文档已经具备，重点是把更具体的边界证明出来。

### A1. DAG 不仅决定先后，还必须决定代码与证据输入

例：A 修改 API，B 依赖 A 开发前端。A 的状态成功不意味着 B 从最初基线创建的 worktree 自动包含 A 的代码。

执行快照应固定 repo identity、base commit、上游 accepted output commits、集成 tree digest、validation profile revision、Harness/image/model 配置摘要，以及节点/尝试身份。B 的输入必须是批准的 A 产物，不是执行时随手读到的活动分支。

A 返工后，应明确哪些后继的产物与批准失效。多个上游的合成树发生冲突，应在下游启动前进入可见的集成阻断，而不是等 closing 再第一次发现。

测试：A-v1 通过→B 成功→A 改成 v2；B 的旧验证和旧评审不能自动覆盖新组合。

### A2. 节点 CAS 之外还需检查图级和项目级不变量

逐节点 revision 比对可以避免本节点陈旧更新，但两个并发请求分别插入 A→B、B→A，若分别依据旧图检查，都可能认为合法。文档已经承诺 reducer 拒绝循环，应验证这个承诺覆盖真实跨进程并发的图修改。

建议只在拓扑/依赖变更等需要时，以最新 graph revision 原子验证并提交；不把所有日志或无关节点更新都锁到全局 Session seq。项目绑定、基线冻结、closing 开始同样要确定其聚合边界。

### A3. “一个结果生效”不等于“外部动作只执行一次”

已有 attempt、lease、claim hash 与首个合法终态生效，只能证明状态接纳端的幂等性；不能自动阻止旧 Worker 在超时之后继续 push 或写外部系统。

Kubernetes 官方指出，即使 parallelism=1、completions=1 且 restartPolicy=Never，同一程序仍可能启动两次。[W2] 因此执行通路应按可能重复或迟到设计。

建议 generation/fencing token 不只写在结果里，还要在可控制的外部写入入口生效。独立 attempt branch；凭证最小权限且可撤销；Host 仅采纳精确预期 commit；必要的外部写入经有幂等键/条件更新的端口。无法让下游检查 fencing 时，不应宣称 exactly-once，而应限制副作用并记录对账责任。

测试：attempt 1 超时但仍活着→attempt 2 完成→attempt 1 最后 push；不能覆盖已经认可的分支/产物，也不能推动错误交付。

### A4. Host 负责验证，并不意味着验证天然可信或安全

状态文档第 230、236 行已经写了 Host fetch、运行验证和集成后复验，不能把“增加 Host 验证”当新发现。真正需要补的是：验证了哪棵精确的树，规则来自哪个版本，执行验证的进程有哪些权限，结果由谁产生并保全。

只允许 `pnpm test` 字符串并不能防止项目内该脚本、测试或构建钩子被改写。建议将验收定义摘要纳入审批；测试配置变更单独提示；验证在确定的候选 tree 上运行；关键质量门槛不由 Worker 同时自由改写。

Git worktree 共享仓库的多数 refs 及默认配置，它不是操作系统安全边界。[W5] DSH 官方也明确不能依赖它作为不可信任务的唯一安全控制。[W6] 对可信本地项目可以保留轻量模式，但必须标出信任假设；对不可信执行使用独立受限环境，不让其持有 Host 的全部凭证、DSH_HOME 与最终合并权限。

### A5. 审批是对内容的批准，而不是永久布尔开关

已有一次性批准和 revision/evidence 核验值得保留。建议进一步明确批准绑定哪些内容：需求/设计/计划摘要、节点集合、候选 tree、验证规则版本、操作范围、风险级别及到期条件。

代码或验证规则变化后，旧批准应自然失效或要求重评。审批消费后 Host 崩溃，应恢复同一个 operation，而不是误视为无批准重开另一笔副作用。前期调研节点仍可就绪即认领；批准绑定与早期执行时间不是同一问题。

界面应给人“决策包”：与上次相比改了什么、凭什么可信、要授权哪项不可逆操作、成本/风险上限、失败后的恢复方式。无需让人翻几十页运行日志来点通过。

### A6. 持久化保证应落到明确故障模型

“状态永不丢失、权限永不越界”超出了当前可证明范围。建议改为可验收承诺：在约定进程崩溃/重启/并发故障下，已确认领域事实可恢复；超出本地磁盘故障范围则依赖备份与恢复方案。是否支持断电级持久性，需要查 DSH append/flush 的实际合同，不能把写入 Promise 成功自动等同 fsync 成功。

保留 Session Event 的领域权威；在其官方能力内记录副作用意图与结果。Git push、K8s create、合并成功到事件落账之间以 operationId 关联、重启对账，避免第二份业务状态数据库。

故障注入覆盖：disk full、尾行截断、追加成功但响应丢失、事件写入失败、快照过时、Config/Workspace 变更、两个 Host 同时重启、旧进程仍存活。任何恢复不能凭空将 unknown 改为 success。

### A7. kubeconfig 路径不是集群不可变身份

计划第 329 行描述以 namespace+kubeconfig path+context 摘要约束清理连接。用户可在相同路径/上下文名下替换配置，指向另一个集群。

建议额外验证可信集群标识、服务端与 CA 信息的配置摘要、目标 namespace UID，并区分凭证轮换与目标集群变化。不要把完整 kubeconfig 或秘密材料写入事件。身份变化时暂停自动清理并要求重新核验，而不是在新集群按旧责任搜索同名对象。

### A8. 成功与清理责任、代码交付与部署，应分开表述

已有 cleanup-pending 独立责任是正确方向。任务成果已验证，不代表其清理责任已结束；清理失败也不应伪装成代码从未提交。

状态文档第 236 行将合并、release event 后推进 `deployed`，但材料没有给出实际部署执行与运行健康验收。对使用者应显示“已合并/已交付”，不宜让其误解为生产已部署。改变领域枚举需用户裁决；不应为了匹配词语自行新增 CD 系统。若保留旧枚举，至少在文案中明确其现有语义。

### A9. 失败关闭之外，需要可操作的恢复与隔离

不要因为任一坏会话或未知账本而永久封锁所有无关工作，也不要为恢复可用性放松身份验证。建议定义阻断范围：某 run、某项目、某池或全局；只有全局不变量破坏才全局停派。提供带精确对象和审计记录的 quarantine/drain/reconcile 操作，不提供万能“强制成功”。

现有严格全局 FIFO 是已定合同，文档第 191 行确认 A 队首被项目配额阻断时 B 不能越过。它会牺牲部分空闲资源利用率，这是选择而不是实现 bug。先展示队首阻塞原因、排队时长与资源空闲；只有用户改变目标后，才改成保持项目内顺序的跨项目可运行队列轮转。

### A10. 多 Harness 的“可调用”与“可交付”分级验收

状态文档第 201 行记录空文本响应通过读取 thinking/reasoning 等字段补充语义。用于诊断协议响应可以有价值，但不应把任意 reasoning 文本当作用户可交付答案。

建议分级：连接成功→协议解析正确→工具能调用→真实任务能产出→Host 能验证→取消/崩溃/清理合同成立。每个适配器声明支持的 API 模式、结构化输出、cwd、工具、取消和证据能力，绑定 Harness/image/protocol 的版本。不同模型之间只统一“明确实现的能力”，不掩盖差异。

### A11. 模型预算与人工注意力也属于编排资源

现有 pool maxConcurrency 解决机器占用，不足以控制一次 run 的无限工具循环、反复失败推理或大量审批打断。建议设置 wall-time、模型调用数、token、工具调用、attempt、日志容量等预算，并记录触发停止的原因；不凭空估算费用。

面向人展示“已完成什么、等待哪项条件、何时需要判断、失败如何接续”，而不是持续滚动全部 token。保留四类人工门禁，通过决策包和通知策略减轻操作负担；不要未经批准删除门禁或改变十阶段合同。

### A12. 有明确的退出与可移交路径

暂停/关闭页面不能与取消持久任务混为一谈。关闭浮层应中止查询；已批准并持久运行的任务是否取消，需要独立明确命令和状态。卸载前应检查活跃任务与待清理责任，决定阻断卸载或显式受控 drain；不能只验 health 404。

即使插件不再启动，也应能导出只读项目摘要、精确 Git 产物引用和未完成责任。旧日志的 reader 版本及安装包可追溯，避免“数据还在但没有兼容 reader”成为事实上的丢失。

## 五、建议的内部架构：仍是单插件、模块化单体

不引入中心服务，不脱离 DSH，不新增第二份项目注册表。可以继续一个发布包，但内部划清以下职责：

| 组件 | 唯一职责 | 禁止拥有的能力 |
|---|---|---|
| DSH Bridge | 生命周期、官方 Remote/Approval/Session 接口适配 | 业务绕过与私有核心 fallback |
| Domain / Reducers | 纯状态折叠、不变量、合法迁移 | 文件、Git、K8s、模型 I/O |
| Command Policy | 身份、内容批准、版本及预算准入 | Worker 任意写状态 |
| Workflow Coordinator | 意图持久化、调度、取消、恢复、closing 顺序 | 执行器协议细节散落其中 |
| Execution Adapters | Local/K3s/Harness 的启动、观察、取消与事实回报 | 最终交付裁决和自批准 |
| Evidence Verifier | 精确产物、运行、验证与来源关联 | 接受 Worker 自报 success 代替证据 |
| Projection / UI | 按各事实源版本呈现、决策包和恢复入口 | 本地乐观制造领域终态 |

关键规则：外部 I/O 一律通过窄端口；模块不接收整个 Host；纯逻辑优先测试；运行与探针共用资源身份/意图/清理协议而不是两套例外规则。把跨进程锁、时钟、环境、Git、K8s、证据存储做成显式端口，以真正的故障注入替代对宿主方法的随意覆盖。

## 六、推荐实施顺序与验收闸门

### 第一批：把“完成”的判断变成机器可执行

补完整可构建导出和官方基线；将 collector 与 gate 分开；修 schema；完成 TTL/精确清理/ZeroProof；保留原始报告；消除当前状态矛盾。第一批不需要新增平台功能。

闸门：故意投喂失败、未知、错版本、缺工件、跳过与残留等反例，均不得得到完整验收通过；同一产物摘要贯穿构建、测试、安装。

### 第二批：优先打通真实本地开发支线

锁定一个小而完整的真实代码需求：建项目、人工决策、派发、本地 Worker 提交、Host 验证、受控合并、责任收尾。失败时先留存最小诊断包，不弱化 no-commit 断言。

闸门：真实模型和本地执行器完成一次成功、一项取消、一项失败恢复；证据能关联到 child/run/commit；不依赖不可访问的临时现场。

### 第三批：验证跨边界的一致性与安全

补 DAG 输入提交、graph 并发、审批失效、过期 Worker 外部写入隔离、未知身份清理、日志前置脱敏、旧项目升级。先限定故障模型，再扩展覆盖。

闸门：重复、迟到、崩溃、断连、磁盘异常与配置漂移不会制造未经批准的交付、错误资源删除或不可发现责任。

### 第四批：用体验与维护性指标减少实际使用成本

改源版本驱动的实时刷新；窄接口重构；失败归因、资源阻断范围、预算与审批决策包。严格 FIFO 是否调整另走用户决策，不混在“修 bug”里。

观察指标：真实需求完成率、人工介入次数/时长、失败定位时长、恢复成功率、排队等待、清理责任年龄、每次有效交付的模型用量。不要只看测试总数、调用次数或“Agent 自称完成”。

## 七、交接给开发 Agent 的范围边界

可直接做的范围：所附独立脚本的明确缺陷、验收语义和证据保全；整理当前状态；在完整源码中补相应回归。

必须先核对源码的范围：运行路径名称补偿、DAG 依赖代码、持久化 flush、fencing、Host 隔离、旧项目续写；本报告不授权把推测当缺陷重写核心。

须由用户裁决的变化：改变节点执行时机、严格 FIFO、公私域/企业平台、十阶段门禁、deployed 枚举含义，以及扩大不可信代码执行的安全承诺。不得借评审进入 Hermes、旧 data-governance 或修改 DSH 私有核心。

本次产物只包含报告、离线探针及证据索引，未修改原插件。
