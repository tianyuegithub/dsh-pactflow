# DSH PactFlow 目标架构（North Star）

本文档定义这个插件的**终局意图**：目的、最终需求、最终想要的系统形态。它是判断一切增量工作"是否跑偏"的对照物，也是整个加固工作的终止条件来源。

它不回答"现在做到哪了"（那是[实施状态](implementation-status-实施状态.md)的职责），也不回答"下一步按什么顺序做什么"（那是 OpenSpec change 与 `openspec/specs/` 的职责）。本文档刻意不包含进度、日期、测试数字和临时阻断——凡是会随时间腐化的内容都不属于这里。

## 1. 文档自身规则

**优先级与事实源**：代码与测试是可执行事实；本文档是终局意图的结构表达。实现与本文档冲突时只有两种可能：实现跑偏（改实现），或目标本身需要演进（走下述变更权流程）。四份文档的分工：

| 文档 | 拥有 | 变更权 |
| --- | --- | --- |
| 本文档 | WHY + 终局 WHAT | **仅用户**；Agent 只能提案 |
| OpenSpec（`openspec/changes/`、`openspec/specs/`、`openspec/config.yaml`） | HOW + 顺序 + 行为合同 | 唯一计划 owner（按 AGENTS.md 规则） |
| [实施状态](implementation-status-实施状态.md) | WHERE-now + 验证证据 | 唯一写入方按证据更新 |
| 本仓库 AGENTS.md | 协作规则 | 用户 |

**回填分流**：实现与实验中发现的问题细节分三类处理，不得混入：

1. 暴露**目标定义本身**有缺陷、遗漏或过时 → 向用户提案，用户确认后修订本文档对应条目；
2. 目标无误、尚未做到 → 作为缺口进入开发计划（合同先行，按 AGENTS.md 规则）；
3. 与目标和计划都无关的纯实现细节 → 只进代码、测试与实施状态证据。

原始实现细节不进本文档；本文档一旦开始记录"某次修复了什么"，它就失去了作为稳定对照物的价值。

## 2. 目的与用户价值

在**未修改的官方 DSH** 上，通过一次安装让用户获得一个可靠的软件开发编排模式（「零脉模式」）：以项目为单位，把需求推进（十阶段与人工门禁）、任务分解（DAG）、施工（本地或 K3s 执行器在隔离任务分支施工）、验证（用户登记的验证配置）、代码收口（受保护默认分支合并）组织为可审计、可中断、可恢复的持久工作流。用户始终拥有审批权与验证配置权；宿主负责门禁、调度与可信落账；执行器只在隔离边界内施工；客户端只展示可重建的真实投影。

一句话：**一个装在官方 DSH 上、状态永不丢失、权限永不越界的软件工程编排插件**。

> 待你确认：以上价值陈述若与你的最终意图有偏差（例如是否需要面向多人/团队协作、是否需要脱离 DSH 独立运行），以你的为准——它们会改变终局能力清单。

## 3. 终局能力清单

完成时，系统必须具备以下能力。每条在验收时必须能独立证明；对应的验收矩阵以[开发计划 §11](development-plan-开发计划.md)为准，此处只定义"要什么"：

1. **官方生命周期**：预构建包对未修改的官方 DSH 完成安装、Profile 激活、启动、升级与卸载，卸载后无残留入口（计划 §1 条件 2；卸载验收需真实 `/api/pactflow/health` 404 证据）。
2. **项目身份**：零脉项目 = 当前 `agentPreset` 投影为 `pactflow` 的根会话 + 绑定项目 Git checkout 的工作区；Session ID 即项目 ID，Settings 中不存在第二份项目注册表（计划 §2.3）。
3. **十阶段与人工门禁**：需求沿十阶段推进，四类人工评审构成持久、可审计的门禁链；评审经 DSH Approval 服务授权，人工不可自批准，旧版本批准事件只读、不解锁新门禁。
4. **DAG 编排**：节点/依赖以每节点 revision CAS 演进；引用缺失、跨需求引用、循环、阶段跳跃、终态复活在事件折叠层被拒绝。
5. **双执行路径**：本地 DSH Subagent 与真实 K3s 多 Harness Worker 共享统一容量调度（FIFO、可取消、重启恢复占用），各自完成过至少一条真实开发任务支线（计划 §1 条件 5）。
6. **用户验证配置**：执行器只运行用户登记的验证 Profile（命令、参数、超时、顺序逐一核对）；任意命令字符串无法进入绑定或执行。
7. **代码收口**：只有宿主在受保护默认分支上完成合并、复验与祖先链核验后才产生交付终态；任务集合核验精确到本次基线；清理责任先于交付记录持久化。
8. **持久恢复**：进程重启后，非终态运行、容量占用、未完成清理责任、探针清理账本全部从持久事实恢复；并发、重复结果、过期租约、崩溃对账有验收（计划 §1 条件 3）。
9. **资源化基础设施**：集群、镜像仓库、Git 提供者、Harness 模板、模型连接、执行资源池六类可引用资源，统一卡片生命周期，删除被引用资源失败关闭。
10. **原生 Web**：Client Module、Slot、Store、Locale、Theme、Typert Remote 全部使用 DSH 原生机制；会话隔离、实时投影、过期响应防护。

## 4. 终局不变量

以下是任何实现都必须满足的边界条件。它们同时是评审自查表：任何改动若触碰其中一条，必须要么符合它，要么走 §1 的目标变更流程。

**事实与权限**
- 领域状态只有一个持久事实源（Session Event）；投影及其缓存永远只是可重建视图。
- Remote 与 Agent 工具不能自行授予批准、不能直接推进交付终态、不能执行任意宿主命令；交付终态只由宿主完成 Git 收口后产生。
- 原始凭证不得进入 Session Log、Remote payload、Tool result、Git、argv、截图或持久日志；Settings 只保存非密钥元数据与 Credential Ref。
- 验证配置登记不是操作系统沙箱：安全声明不得超出"已登记命令按精确内容执行"的范围。

**执行与清理**
- K3s 结果必须与精确身份绑定：Job/Pod 所有者、镜像完整 digest、Spec digest、分支、基线提交、claim 哈希；prompt 不进入 ConfigMap。
- 持久资源的删除一律携带 UID 前置条件，404 幂等，非 404 错误不得吞掉；从未确认身份的资源绝不按可重用名称删除。
- 清理责任必须持久、可发现、可重试；崩溃窗口内身份未确认的记录保留并失败关闭，不自动猜测目标。
- 每任务一分支一 worktree；Worker 只提交任务分支，只有宿主在 closing 阶段合并受保护默认分支。

**并发与恢复**
- 并发写入以 revision CAS + 跨进程文件锁保护；损坏文件失败关闭，不覆盖。
- 取消必须贯通：用户取消、宿主时限与执行器信号一致，关闭浮层即撤销在途请求。

**形态与兼容**
- 不存在 iframe、第二层 Web 壳或私有 DSH 源码导入（计划 §1 条件 4）。
- 旧版本事件只读兼容；生产安装必须在未修改的官方 DSH 上；需要 DSH 新通用能力时，走独立上游 change 并等待进入受支持发行版，禁止私有 patch 回落。

## 5. 永久非目标

以下事项**永远不在**本插件范围内，任何"接着完善"都不得扩张到这些边界：

- 与 Hermes 版零脉共享、读取或复用其源码、数据库、协议或运行时；两者是独立产品实现。
- 修改 DSH 核心源码、发布私有核心 patch、把产品 Package 放入 DSH `packages/` 树。
- 旧 `data-governance` 工作区的任何改动。
- 在 Settings 内维护第二份项目注册表，或让外部 Worker 直接写 Session Log。
- 基于可修改字段（如 Gitea 描述）、同名资源或模糊 API 结果自动认领外部资源所有权。
- 远程/企业平台形态（决策 3，2026-09-06）：kubeconfig 上传与托管、多租户隔离、中心化服务端组件。kubeconfig 永远只是本地文件引用。

> 注意：npm 发布时机、官方 DSH 版本兼容、历史无所有者 Pod 的处置等属于**临时阻断**，由实施状态与计划记录，不属于本节——阻断解除时它们自然消失，不影响终局定义。

## 6. 目标决策记录

以下事项曾长期待决，现已由用户裁决（2026-09-06），结论具有合同效力，修改须走新的目标变更：

1. **任务图节点准入：维持就绪即可认领（选项 B）**。认领仅检查节点就绪（依赖满足），不将节点限定为计划获批后的实施任务，允许前期调研类节点提前执行。这是有意的灵活性取舍；十阶段门禁约束的是阶段推进与评审记录，不约束节点执行时机。任何"收紧认领"的实现都属跑偏。
2. **创建结果不明的仓库对账：采用半自动恢复（选项 A）**。对处于"结果不明"状态的远端创建责任，宿主提供只读候选查询与人工确认入口：候选仓库与持久化意图逐项比对（所有者、名称、可见性、默认分支）后展示；仅当用户确认**精确仓库编号**且宿主按编号复核仍精确匹配时，才持久化远端地址并接续推送。描述字段与操作编号只作关联线索，永远不构成所有权证明。
3. **远程企业平台：排除（选项 B）**。kubeconfig 上传/托管、多租户隔离、中心化服务端组件不属于终局范围；本插件终局为本地单机形态，kubeconfig 永远只是本地文件引用（已列入 §5 永久非目标）。

## 7. 完成的定义

完成 = 计划 §1 的六项完成条件全部满足，且闭合以下架构级规则：

- §3 的每条终局能力，要么有相称的**真实**验收证据（记录于实施状态），要么在计划中有显式合同并标记为缺口——不存在既无证据又无合同的"隐性未完成"。
- §4 的每条不变量都有对应的可证伪测试或真实环境验收，且未被后续改动削弱。
- §5 的边界无一被越过；§6 的决策项要么已确认并落实，要么显式保持暂停。
- 未运行、被跳过或被环境门控的验证不得计为通过；本地通过不替代官方安装与真实环境验收。

满足以上全部条件时，加固工作终止；此后本插件进入维护态，任何新能力都重新走目标确认 → 计划合同 → 实现验收的完整流程。
