# k3s-resource-identity Specification

## Purpose
为 K3s 运行与探针在执行期间创建的所有 Kubernetes 持久资源建立可核验的身份链：创建前先持久化授权意图，创建后以服务端返回的 UID 确认归属；只有已确认归属的对象才可被删除；身份未知或创建结果不明时保留责任并失败关闭，绝不按可重用名称猜测删除。

## Requirements

### Requirement: 创建外部资源前必须先持久化授权意图

在创建任何 Kubernetes 资源之前，Host SHALL 先持久化本次操作的授权意图，至少包含：操作编号、Provider/集群身份、namespace 身份、资源种类、选定的临时名称或受控分配规则、数量上限、允许动作、用途与清理范围。意图写入失败时 Host MUST 拒绝创建外部资源，MUST NOT 先创建再补写。

#### Scenario: 意图落盘失败则不产生孤儿资源

- **WHEN** 清理账本/意图存储写入失败
- **THEN** Host 不创建任何 Kubernetes 资源，并返回明确失败

#### Scenario: 新建意图不含虚构 UID

- **WHEN** 创建前写入意图记录
- **THEN** 该记录不含任何 UID 字段，创建后由回执补充精确 UID

### Requirement: 创建回执必须以服务端 UID 确认归属

创建请求成功返回后，Host SHALL 立即持久化服务端返回的精确 UID 与相关版本，并将其纳入本次操作的已确认资源集合。只有进入该集合的对象才被视为本轮拥有。

#### Scenario: 成功创建后纳入 owned 集合

- **WHEN** 创建 Secret/ConfigMap/Job 并收到含 UID 的成功响应
- **THEN** Host 持久化该 UID 并将对象标记为本轮已确认归属

#### Scenario: 无 UID 的成功响应不得当作可删除依据

- **WHEN** 创建响应缺少有效 UID
- **THEN** Host 不将该对象纳入 owned 集合，并按身份未确认处理

### Requirement: 只有已确认归属的对象可被删除

Host SHALL 仅对 owned 集合中具有精确 UID 的对象执行删除，并使用 UID 前置条件；删除不要求对象预先具备 Job ownerReference。创建返回 409（AlreadyExists）的对象从未属于本轮，Host MUST NOT 因本次创建失败而删除同名对象。当读到同名但 UID 不同的对象时，Host MUST NOT 删除该替代对象。

#### Scenario: 创建冲突不删除既有对象

- **WHEN** ConfigMap 创建返回 409，现场存在同名但非本轮的既有对象
- **THEN** Host 对该既有对象发出的删除请求数为 0，并明确报告创建冲突失败

#### Scenario: 同名替换不被删除

- **WHEN** 归属校验后、删除前，同名对象的 UID 已变为另一个值
- **THEN** Host 不删除该替代对象，并记录原 UID 已不在该名称上的事实

#### Scenario: 已确认归属的孤儿可被精确回收

- **WHEN** 本轮创建的对象已持久化 UID，且该对象是唯一残留
- **THEN** Host 以 UID 前置条件删除该对象，404 视为幂等成功

### Requirement: 创建结果不明必须保留责任且失败关闭

当创建请求超时或响应丢失时，Host SHALL 将该资源记录为 `create-outcome-unknown`，MUST NOT 假定未创建，MUST NOT 仅凭名称或标签自动认领或删除。若在结果未定时暂时读到 404，Host MUST NOT 据此单次读取清除创建意图，MUST 覆盖迟到创建窗口或保持显式 unknown。

#### Scenario: 创建超时保留 unknown 责任

- **WHEN** 创建请求超时且无法确认服务端结果
- **THEN** Host 记录 unknown 责任并保留对账入口，不对该名称发起兜底删除

#### Scenario: 迟到创建不被一次 404 抹除

- **WHEN** 结果未定的资源先读到 404，随后该资源实际出现
- **THEN** Host 在观察窗口内仍保留创建意图，不将其判定为不存在

### Requirement: 删除受理不等于删除完成

Host SHALL 区分「删除请求被接受」与「指定 UID 对象已消失」。删除返回 202 或对象处于 terminating（受 finalizer 约束）时，MUST 记录为 `delete-requested` 或 pending，MUST NOT 计为清理完成。删除超时、403 或连接错误 MUST 保留责任、原因与下次对账条件，MUST NOT 当作 404。

#### Scenario: finalizer 延迟不冒充已清理

- **WHEN** 删除请求返回 accepted，但对象因 finalizer 仍存在
- **THEN** Host 将该清理记录保持 pending，不报告零残留

#### Scenario: 删除失败保留责任

- **WHEN** 删除请求超时或返回 403
- **THEN** Host 保留该清理责任并登记重试条件，不将其记为成功

### Requirement: 失败路径必须释放本运行的内存秘密引用

运行/探针准备阶段暂存的内存秘密引用（`pendingRuntimeSecrets` 等）SHALL 在成功、失败、取消、超时与准备对象丢弃的每条终态路径上被释放。释放 MUST NOT 通过删除身份不明的外部资源来实现。释放内存引用 MUST NOT 被表述为已撤销远端令牌；两者分别验收。

#### Scenario: 创建失败后不残留本运行秘密

- **WHEN** 创建流程在绑定完成之前失败
- **THEN** 本运行对应的内存秘密表项回到基线，且不触发任何按名称的外部删除

#### Scenario: 取消与丢弃路径同样释放

- **WHEN** 准备完成后请求被取消或准备对象被丢弃
- **THEN** 对应的内存秘密引用被释放，且未确认身份的外部资源不被删除

### Requirement: 对账绝不回收仍在执行的资源

按已确认 UID 删除一条持久清理责任所指的 Job 之前，Host SHALL 先确认该 Job 已非活动状态。Job 仍在执行时，Host MUST 保留该责任并交由重连恢复路径处置，MUST NOT 删除。活性无法读取时 MUST 按「仍在执行」处理——不知道不是销毁的许可。Job 已不存在或其 UID 与记录不符时，按既有规则继续对账。

该条与既有的「创建前先落意图、只删已确认归属」互补：那两条防的是孤儿资源，这一条防的是**对账本身成为破坏源**。宿主崩溃重启恰好是「记录已确认、Job 仍在跑」的时刻，而删除使用 `gracePeriodSeconds: 0` 与 Background 传播，销毁的是正在进行的真实模型执行与它已经产出的提交；并发的恢复路径随即观测到资源消失并把该 Run 判为失败。

#### Scenario: 重启时在途 Job 不被删除

- **WHEN** 启动对账读到一条已确认 UID 的 Run 清理责任，而该 Job 在集群中仍处于活动状态
- **THEN** Host 不发出任何删除请求，保留该账本条目，并记录该责任交由恢复路径处置

#### Scenario: 活性未知时保留责任

- **WHEN** 读取该 Job 状态失败（API 不可达、超时）
- **THEN** Host 不删除、不移除账本条目，并将本次对账判为未完成

#### Scenario: 终态 Job 照常对账

- **WHEN** 该 Job 已进入成功或失败终态，或已不存在
- **THEN** Host 按既有 UID 前置条件规则删除其已确认归属的子资源与 Job，并移除账本条目

### Requirement: 正常清理必须使账本收敛

一次运行的资源被正常清理后，Host SHALL 落账该责任已完成，使该条目从账本移除。MUST NOT 依赖启动对账作为唯一的移除路径。

否则账本随每次完成的运行单调增长，且每次宿主重启都对已经消失的资源重放一轮删除。

#### Scenario: 清理完成后条目消失

- **WHEN** 一次运行的 K3s 资源被正常清理成功
- **THEN** 该运行在清理账本中不再存在

### Requirement: 账本中无法读取的记录一律失败关闭

加载持久清理账本时，任何无法按当前结构读取的单条记录 SHALL 使整次加载失败并指名账本已损坏。MUST NOT 跳过该记录后继续。

跳过不是惰性行为：账本的持久化是整文件覆盖，跳过一条即在下一次写入时把它永久删除，且日志里没有任何提示，它所指的集群资源从此无人负责。升级时新增一个必填字段就足以触发——现有的 Provider 指纹字段当初正是这样加入的。

#### Scenario: 缺少当前版本必填字段的记录使加载失败

- **WHEN** 账本中存在一条缺少当前版本必填字段的记录
- **THEN** 加载失败并指名账本损坏，原文件不被改写

#### Scenario: 拒绝加载本身不得破坏账本

- **WHEN** 因上述原因拒绝加载
- **THEN** 磁盘上的账本内容保持不变

### Requirement: 账本的读改写在跨进程锁内进行

对持久清理账本的每一次修改，Host SHALL 在跨进程文件锁内完成「从磁盘重读 → 修改 → 写回」，MUST NOT 依赖进程内的一次性缓存视图。一次写入失败 MUST NOT 使该进程后续的写入永久失效。

同一 `DSH_HOME` 可能同时被两个宿主进程使用（升级并行期、安装校验与正式实例共存、端到端验收与真实实例并行）。各持一份陈旧内存 + 整文件覆盖意味着后写者抹掉前者记录的清理责任，而任何对账都发现不了——它读的正是同一份陈旧内存。

#### Scenario: 另一进程写入的责任不被抹除

- **WHEN** 进程 A 记录了一条责任，进程 B 随后记录另一条，进程 A 再次写入
- **THEN** 两条责任在磁盘上同时存在

#### Scenario: 一次写入失败后仍能继续记录

- **WHEN** 一次账本写入因 IO 错误失败
- **THEN** 该次操作向调用方报错，其后的记录操作仍被真实尝试并可成功

### Requirement: 创建意图记录计划中的子资源名且该清单不得用于删除

创建意图 SHALL 记录本轮计划创建的子资源名称。该清单 MUST 被明确标注为诊断用途，MUST NOT 被任何删除路径当作归属依据。

意图的用途是让「创建请求已发出、回执未到达」的崩溃窗口留下可发现的责任。此时不存在任何 UID，若连计划中的名称也不记录，人工恢复者无从得知本轮打算创建什么。但名称不是身份，仍然只有带精确 UID 的对象可被删除。

#### Scenario: 意图记录中含计划名称但不含身份

- **WHEN** 写入一条含若干计划子资源名的创建意图
- **THEN** 该记录含这些名称，且不含任何 UID 或已确认归属集合

### Requirement: 无确认身份的取消一律失败关闭

取消一次运行时若不存在已确认的 Job UID，Host MUST 失败关闭并保留该责任，MUST NOT 按可重用名称删除任何资源，MUST NOT 把删除超时当作已清理。按可重用名称删除的实现 MUST NOT 存在于代码中，即使当前没有调用者可以到达它。

一条当前不可达的违规分支不是无害的：它是下一个调用者可以获得的能力，而它与同一模块中正确实现的补偿路径自相矛盾。

#### Scenario: 无 UID 的取消被拒绝

- **WHEN** 取消一次尚未确认 Job UID 的运行
- **THEN** Host 报错并说明责任保留待显式恢复，对该运行的资源发出的删除请求数为 0

### Requirement: 集群身份不得退化为 kubeconfig 路径

解析集群身份时，若证书颁发机构材料需从文件读取而读取失败，Host MUST 失败关闭，MUST NOT 以该文件路径代替其内容参与身份摘要。

以路径代替内容正是该身份机制存在的理由所否定的东西：路径上的文件可以被替换为指向另一个集群的配置。一次瞬时读取失败若使指纹静默退化，「kubeconfig 被掉包」从此检测不到，而清理对账正是以该指纹匹配 Provider。

#### Scenario: CA 文件不可读时拒绝建立集群身份

- **WHEN** kubeconfig 指向的 CA 文件因权限或缺失而读取失败
- **THEN** Host 报错并指明集群身份无法建立，不产生任何以路径为材料的指纹
