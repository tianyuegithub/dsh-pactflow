# design — dsh-harness-telemetry

## 关键决策

### 1. 推翻的不是结论，是前提

此前「这两级不可证、token 不可得」的结论没有错，错的是它依据的前提——「执行器不归本仓管」。

实际上执行器分两类：**第三方 runner**（claude / codex / opencode）确实不归本仓管；**`dsh` 执行器的适配插件归本仓管**，项目规则明确允许「容器内 DSH 执行器可由本仓库维护适配插件与源码补丁，按固定镜像摘要独立分发」，`release-manifest.json` 的 `adapterVersion` 就是这条规则的落地。

因此结论要按 Harness 分裂，而不是整体推翻或整体保持。**这决定了本 change 的核心形态：可证集合从全局常量变成按 Harness 一份。**

### 2. 两个失败模式：往上冒充，往下冒充

**往上冒充——把宿主的能力记成 Harness 的能力。** 验证本来就由宿主执行，「跑一条验证命令」随时可做。据此点亮 `verification` 级，所有 Harness 都会瞬间"达到"，一个本来诚实的阶梯变成一律虚报。spec 写死：以 runner 回报为准；对抗性测试：宿主执行了验证但 runner 未回报 → 不得声称。

**往下冒充——拿低一级的观测点亮高一级。** 这是评审补的，首版没防。`artifact` 级的观测是 `cli-response`：runner 跑一条命令回结果。如果「验证阶段」也只是让 runner 跑一条命令，那它证明的还是 `artifact`，只是换了个名字点亮了更高一格。**两级必须有观测上的差异，否则高一级没有独立含义。**

定义出来的差异：`verification` 级要求 runner **按验证协议执行多步、顺序敏感、绑定 Profile 身份的任务，回报逐步结构化报告**，宿主逐项核对。只会跑 shell 的 runner 回的是一个块，产生不出逐步有序报告。探针用一个临时两步合成 Profile 触发（步 1 写标记、步 2 断言标记存在，顺序反了就失败），结束后不残留。

这个定义也回答了「为什么 `verification` 对第三方 Harness 不可证」：它们的 runner 没有实现验证协议，回不出逐步报告——不是本仓不想测，是观测本身产生不出来。

### 2a. 可行性先行

工具调用上报要在容器内 DSH 的工具执行链上挂钩；token 用量要从容器 DSH 的会话里取。容器 DSH 钉的是 `0.1.1-rc.2`。fork 里有 `packages/hooks`，但**钉版的那个版本有没有可用的钩子接口、有没有暴露用量，没查**。

首版列了 22 条任务却没有这一步。任务 0 改为 spike：在现有镜像里各试一次，拿三种结论之一——可行 / 不可行 / 需升级容器 DSH 版本。不可行时本 change 缩为只做 `verification` 级（它走结果文档，不依赖钩子）。升级容器版本是独立决策（涉及 `dshVersion` 钉版与全部远程交互验收重跑），不在本 change 内默默做。

### 3. 「不可得」必须是一等状态，不能是 0

token 用量不可得时记为 0，会造成两种具体错误：预算判定认为「这次没花钱」；跨运行汇总时把不可得的运行算作零成本，使总量系统性偏低。

因此不可得是一等状态，与「可得且为 0」严格区分，且不可得的用量 MUST NOT 参与任何预算判定。这与 A05 保留现场 `sizeBytes` 的既有处理同源——「未测量」不谎报为「总量为 0」。

### 4. 既有三项预算维度保持单一权威

`harden-output-budget-authority` 已经把「输出上限由预算单一权威决定」钉死。新增用量维度时最容易破坏的就是这条：一旦用量参与输出截断判定，就出现了两个权威。

因此用量是**并列的新维度**，不介入既有三项各自的判定。

### 5. 不新增事件类型

用量与工具调用计数走既有运行结果 payload 的可选结构化字段，与 `artifact-ref-handoff` 的处理一致。理由同样是：这些是既有领域对象（Run）的附加观测，不是新领域对象。

### 6. 清单版本漂移拆出去了

首版把 `hostEventProducerVersion` 漂移（`0.5.0` vs 代码 `0.6.0`）的修复捎带在本 change。评审指出：改数字 + 补守卫是半小时的事，塞进一个要重建镜像、上真实集群的 change 里，等于让一个已知错误再挂几周。已拆为独立小 change `manifest-producer-version-guard`（Modified `operator-doc-accuracy`）。

本 change 与它的关系：本 change 升 `adapterVersion` 重新钉版时，守卫应已在（绿）；钉版后该字段由守卫钉住，本 change 不需要再单独处理它。首版「先钉版再改数字」的顺序论证仍然正确——但那是对*本次新镜像*的约束，不妨碍守卫现在就加上。

## 不做什么

- **不为第三方 Harness 伪造上报**：不在宿主侧"推断"claude/codex/opencode 是否调用了工具。
- **不做跨 Harness 能力协商**：属新能力，且当前无消费场景。
- **不做成本换算与计费**：token 数是观测，单价与计费是另一回事，涉及模型供应商定价的持久化，属新目标。
- **不改第三方 runner 镜像**：不在本仓所有权内。
- **不扩大安全承诺**：只增加观测与计量，工具作用域、沙箱声明与 Worker 权限边界一律不动。

## 未决问题

- **验证阶段探针的形态**：是在既有能力探针里加一个阶段，还是单独一次探针运行？前者省一次集群往返，后者边界更干净（验证阶段可能有副作用）。倾向前者，但需在实施时确认验证阶段确实无副作用。
- **用量的聚合粒度**：按 Run 记录是确定的；是否需要按 Need 或按项目聚合呈现，留待真实使用后再议，本 change 不预先设计。
- **`adapterVersion` 升到几**：三项上报是行为新增而非不兼容变更，倾向 `1.1.0 → 1.2.0`。需在实施时按既有版本语义确认。
