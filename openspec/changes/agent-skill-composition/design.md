# design — agent-skill-composition

## 关键决策

### 1. 用 DSH 原生 skill 机制，不自建知识加载

DSH 的 skill 组已提供完整形态：注册表（`@deepseek-ai/dsh-skill`）合并多个提供方的目录并为每个名称解析出胜出者；文件系统提供方（`@deepseek-ai/dsh-skill-filesystem`）从本地项目、用户目录或随包分发的目录贡献；消费方（`@deepseek-ai/dsh-tool-skill`）把可用 skill 发布为持久会话目录并提供面向模型的加载工具，用户也可 `/name` 直接调用。

零脉需要的正好是这套东西。自建等于在 Agent 面重演一次「不用原生机制」的错误——那是架构 §4「不存在 iframe、第二层 Web 壳或私有 DSH 源码导入」在 Client 面已经守住的边界，Agent 面同理。

**分发路径是现成的**：preset 已有 Package-owned root（`pactflowPresetRoot`，由 `cordis.patch.yml` 注入 `agent-presets`）。skill 目录随包走同一条路。

### 2. Workflow Consumer 为什么砍

见 proposal。要点：脚本能做的只剩「多发几次 dispatch」；与宿主持久的 `need-autopilot` 是两个编排器；DSH 自己说它不是安全边界。等具体用例。

### 3. 红线留 persona，知识进 skill —— 切分判据

判据只有一条：**这条内容如果模型没主动加载就会出事吗？**

- 会出事 → 留 persona。例：「不得自行授予或伪造人工批准」。
- 不会出事，只是做得不够好 → 进 skill。例：「单节点优先的拆分判据」。模型不加载它，最坏结果是拆得不合理，而不合理的拆分仍然要经方案确认由人否决。

这条判据同时给出了守卫测试该测什么：**红线不得改由 skill 承载**。把「不得自批准」挪进按需加载的 skill，就把一条硬约束变成了「模型记得加载才生效」——这是本 change 最危险的失败模式。

### 4. 守卫怎么做

首版写「按语义断言」，评审指出这是把部分字符串匹配包装成了更高级的东西。诚实的说法：**结构化红线清单 + 逐条关键约束要素检查**。它确实是字符串层面的检查，但检查的是每条红线的约束要素是否存在，而不是整串是否相等。

两个边界都写进 spec：不得退化为整串比对（那会让每次文案润色都红，最终导致守卫被放宽）；不得松到非空即过。

### 5. 收缩 persona 是行为变更，要用真实模型套件兜底

这条是评审补的，也是首版最大的遗漏。`test:real-worker`、`test:autopilot`、`test:worker-interactions` 三个真实套件的通过都依赖当前 persona 的措辞。收缩后模型可能漏掉某个此前靠 persona 常驻才记得的步骤。

因此三个套件重跑通过是**合入条件**，不是「建议做」。这与「未运行、被跳过的验证不得计为通过」是同一条纪律。

收益也要实测：收缩前后系统提示字节数对比记入实施状态，不凭估计宣称。

### 6. Skill 与业务逻辑文档：单一来源

后三个 skill（收口三层门禁、七类资源登记、异常速查）的内容来自 `docs/business-logic-业务逻辑.md` §6 / §2.1 / §9。复制进 skill 就是两份正文，必然漂移。

两个选项：skill 从文档生成；或 skill 是正文、文档指向 skill。

**选后者**。理由：skill 是给模型读的、有格式约束（名称 + 简短描述 + 正文），文档是给人读的、可以随意排版；让文档生成 skill 需要一个生成器和一套格式约定，成本高于「文档写一行指向」。业务逻辑文档本就是派生视图（其开头写明「正文以 openspec specs 为准」），指向 skill 不改变它的 owner 地位。

### 7. Skill 正文也是进入模型上下文的文本

与 `need-comment-threads` 中的评论同族——它是新的文本源。区别是 skill 内容由本仓分发、经过评审，不是用户或模型在运行时写的。风险低，但仍复用 DSH 原生 skill 机制的来源标记，不另造。

### 8. 首批 skill 的选取

| skill | 来源 | 何时需要 |
| --- | --- | --- |
| 执行方案拆分判据 | persona（现有） | 要派发时 |
| 本地恢复候选比对 | persona（现有） | 上次本地执行失败留有候选时 |
| 挂机授权边界 | persona（现有） | 存在挂机授权时 |
| 收口三层门禁 | 业务逻辑 §6（模型读不到） | 进入 closing 时 |
| 七类资源登记 | 业务逻辑 §2.1（模型读不到） | 配置基础设施时 |
| 异常速查 | 业务逻辑 §9（模型读不到） | 遇到错误时 |

后三条是**净增能力**——这些知识此前对模型完全不可见。

## 不做什么

- **不做 Workflow Consumer**：见 proposal。
- **不做远程 skill 提供方**：需要服务端，与「本地单机形态」冲突。
- **不接管用户自有 skill 目录**：DSH 原生机制已承载。
- **不注册 `ralph` 工具**：全新 agent 迭代循环与零脉「每任务一分支一 worktree、经门禁推进」的模型不兼容。
- **不改任何现有工具的语义与权限**。

## 前置核实

MUST 核实目标 DSH 发行版随附 `@deepseek-ai/dsh-skill`、`@deepseek-ai/dsh-skill-filesystem`、`@deepseek-ai/dsh-tool-skill` 三个包。当前证据来自 fork 工作树，**是工作假设**。官方发行版目前连 `externalEventProducers` 都没有，所以「对官方核实」今天做不了——目标发行版出现前以 fork 为准并如实标注；出现后若缺任一，本 change 转上游阻断，MUST NOT 私有 patch 回落。

## 未决问题

- **skill 的粒度**：六个是首批估计。真实使用后按会话观测调整。
- **persona 收缩的边界**：哪些内容算「场景化」、哪些算「红线」，判据清楚但具体划分可能有争议。实施时把划分结果列成表交人确认，再动 persona。
