# node-rerun-authorization

## Why

`retryNode`（`src/index.ts:1921`）显式拒绝非失败态：

```
PactFlow node "<id>" cannot retry from state <state>
```

只有 `failed` 与 `cancelled` 能回到 `ready`。成功的节点是终点，没有任何路径让它按新输入重做。

这造成两个具体损失：

1. **依赖链上游变更后，下游无法局部重做**。节点 B 以节点 A 的提交为代码输入并成功；此后 A 因缺陷被重跑并产生新提交。B 当前只能有两种下场——要么带着过期输入停在「已成功」（事实上已经不对了），要么新建一个内容重复的节点，让 DAG 长出与 B 语义相同但身份不同的第二个节点，历史与审批链就此分叉。
2. **`code-input-staleness` 交付即死码**。该检测器（`src/input-staleness.ts` 的 `staleCodeInputs`）2026-09-11 随 change `harden-input-staleness` 交付并通过测试，但它的触发前置是「前序成功后再重跑」——该能力不存在，所以这段代码在生产中**永远不会执行**。这是仓库里唯一一处「功能完整、合同齐备、但结构上不可达」的实现，长期挂在诚实清单里。

2026-09-11 曾裁决「保持现状、不新增该能力」。**用户于 2026-09-15 推翻该裁决**，本 change 据此立项。

## 与架构文档的冲突（需用户裁决）

架构 §3 终局能力 4 现写：

> 节点/依赖以每节点 revision CAS 演进；引用缺失、跨需求引用、循环、阶段跳跃、**终态复活**在事件折叠层被拒绝。

允许 `succeeded → ready` 就是终态复活。**本 change 在有意削弱这条不变量**，不回避这一点。

首版方案曾以「`retryNode` 已经把 `failed`/`cancelled` 恢复为 `ready`，所以措辞早已不字面成立」来减轻分量——评审指出这是偷换：`failed`/`cancelled` 是*失败*终态，没有任何下游拿它们的产物当输入；「终态复活被拒绝」的意图明显针对的是 `succeeded`——那个下游依赖其提交的状态。拿失败重试当先例论证成功重跑，是弱论证，已撤回。

诚实的表述是：这条不变量保证「`succeeded` 意味着永久、下游可以依赖」。本 change 削弱它，换取「上游变更后下游可局部重做」，并以三条补偿把削弱限制在可控范围内——**所有者显式授权**（不是任何自动路径）、**历史 Run 全保留**（历史不被改写）、**下游只标记不级联**（削弱不传播）。补偿是否足够，由架构措辞裁决决定。

**提案（架构文档变更权仅用户，此处只提案不改）**：把该分句改为

> 引用缺失、跨需求引用、循环、阶段跳跃、**未经所有者显式授权的终态复活**在事件折叠层被拒绝。

若用户不接受该修订，本 change MUST 改走「不复活」的备选路径（见 design.md「备选方案」），或整体撤回。**在架构措辞裁决之前，本 change 的实施任务不得开始。**

## What Changes

- **新增所有者授权的重跑**：独立于 `retryNode` 的新入口，`succeeded → ready`，要求显式授权 + 节点 revision CAS。旧 Run 记录、claim、outcome 与 attempt **全部保留**，新 attempt = 既有最大值 + 1，MUST NOT 覆盖历史。
- **重跑必须重解析代码输入基线**：重跑前 MUST 重新解析全部依赖的当前提交，`staleCodeInputs` 在此路径真正生效——过期项 MUST 在授权界面上如实呈现给人，作为「是否值得重跑」的依据。
- **下游不级联、只标记**：重跑成功产生新提交后，以本节点为代码输入的下游已成功节点 MUST 被标记为输入过期并对人可见，MUST NOT 自动重跑、MUST NOT 自动改变其状态。是否重跑下游是人的决定。
- **失败关闭**：存在任何未过期的活跃 Run 时拒绝；节点已进入交付终态（其提交已合并入受保护默认分支）时拒绝；`archived` 节点拒绝；`paused` 节点拒绝（须先显式 resume）；需求处于 `closing` 或 `deployed` 阶段时拒绝。
- **审批失效贯通**：重跑改变交付对象，既有的验证批准 MUST 随之失效——复用既有 `review-subject-binding` 的漂移检测（`PactFlow delivery subject changed after verification approval`），MUST NOT 让重跑绕过它。
- **预算**：重跑消耗运行预算并按既有 `run-budgets` 合同计入 attempt 上限；耗尽时进入既有的持久 `paused` 语义，不另设第二套。
- **Agent 面**：模型 MUST NOT 自行发起重跑。重跑是所有者决定，经既有原生方案确认路径取得人的明确选择后由宿主执行；Agent 可读过期标记并在方案中**建议**重跑。
- **挂机不得代为授权重跑**：`need-autopilot` 允许「在有效授权范围内自动选择推荐方案」——若不排除，模型推荐一个含重跑的方案 → 挂机自动选中 → 重跑被授权，**全程没有人**，直接推翻上一条。本 change 把重跑**排除在挂机可自动选择的范围外**：推荐方案含重跑时，挂机 MUST 暂停并把该方案交人显式选择，MUST NOT 自动选中。理由：重跑是对已成功工作的主动重做，不是「推进到交付」；自动重跑还会形成「重跑 → 下游过期 → 重跑下游」的预算黑洞。
- **失败关闭的判定不可得时同样拒绝**：「是否已合并入默认分支」需要一次 Git 祖先链查询；远端不可达、引用缺失、查询超时等使判定不可得时 MUST 拒绝重跑并指名原因，MUST NOT 以「查不到就当没合并」放行。
- **正在运行的下游也要标记**：以本节点为代码输入、当前处于 `running` 的下游节点消费的是旧输入，其结果落账时 MUST 立即标记为输入过期，与已成功下游同样处理。
- **非目标**：不做自动级联重跑；不做「重跑整个 DAG」；不做已合并提交的回滚；不做跨需求的重跑。

## Capabilities

### New Capabilities

- `node-rerun-authorization`: 已成功节点在所有者显式授权下重跑的完整行为合同——授权与 revision CAS、历史 Run 与 attempt 的完整保留、重跑前重解析代码输入基线、下游只标记不级联、五类失败关闭、审批失效贯通、预算与暂停复用、Agent 面不得自行发起。

### Modified Capabilities

- `code-input-staleness`：新增「过期检测必须在重跑授权路径上真实生效」Requirement，把此前不可达的检测器接入真实触发路径，并要求过期项在授权决策点对人可见。
- `need-autopilot`：新增「挂机不得自动授权重跑」Requirement——含重跑的推荐方案不在挂机可自动选择的范围内，挂机遇之 MUST 暂停并交人显式选择。

## Impact

- **Host**：`src/index.ts`（新增重跑 `@Remote()`，与 `retryNode` 分离；五类失败关闭；审批失效贯通）、`src/domain.ts`（fold 层允许经授权的 `succeeded → ready`，未授权路径继续拒绝；下游过期标记进 DAG 投影，`stateVersion` 升级）、`src/input-staleness.ts`（接入真实调用点，函数本身预期无需改动）。
- **Session Event**：**不新增事件类型、不升生产者版本**——重跑经既有 `pactflow/node-updated` 表达，授权证据与过期快照走 payload 可选结构化字段。
- **Client**：授权入口须在决策点展示「哪些依赖的代码输入已过期、从哪个提交变到哪个提交」；DAG 呈现下游过期标记。
- **Agent**：不新增写工具；`pactflow_view` 快照补过期标记；执行方案中可建议重跑。
- **挂机（need-autopilot）**：`src/host/autopilot-driver.ts` 的自动选择逻辑识别「方案含重跑」并拒绝自动选中，转为暂停并交人。
- **与 `gitea-review-gate-closure` 的耦合**：本 change 失败关闭第 2 条「已合并入默认分支 → 拒绝重跑」正是为该 change 的「外部手工合并」场景而设（否则它与第 5 条「需求处于 closing/deployed」几乎重叠）。两个 change 互为前提，任一先实施均可，后实施者 MUST 复核前者的对应场景仍成立。
- **Worker Provider**：不涉及（重跑走既有派发路径）。
- **架构对应**：§3 终局能力 4（DAG 编排）——**需先取得措辞修订裁决**；§4 不变量「并发写入以 revision CAS 保护」「取消必须贯通」被本 change 的失败关闭条款显式覆盖。
- **前置**：架构 §3 item 4 措辞裁决未决之前，实施任务不得开始。
