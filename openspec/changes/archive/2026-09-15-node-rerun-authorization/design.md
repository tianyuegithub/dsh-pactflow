# design — node-rerun-authorization

## 前置：架构措辞裁决

本 change 的实施任务 **MUST NOT 在架构 §3 终局能力 4 的措辞裁决之前开始**。提案见 `proposal.md`「与架构文档的冲突」。若用户不接受修订，改走下文「备选方案」或整体撤回。

这条不是形式主义。架构文档是判断一切增量工作「是否跑偏」的对照物；在它仍写着「终态复活被拒绝」时实现终态复活，等于让实现与对照物同时失真，此后任何评审都失去基准。

## 关键决策

### 1. 重跑与重试分离为两个入口，不合并进 `retryNode`

`retryNode` 的语义是**失败恢复**：前提是出了问题，目标是把同一件事再做一次。它的预算语义、错误文案、暂停逻辑都围绕这个前提。

重跑的语义是**主动重做**：前提是输入变了，目标是让输出跟上。它需要额外的授权证据、需要重解析基线、需要触发下游标记——这些对 `retryNode` 都是噪声。

把两者塞进一个入口，会让 `retryNode` 出现「这次是失败重试还是主动重做」的分支判断，而该判断只能靠调用方传参表达——那就等于两个入口共用一个名字。

### 2. 不级联：只标记下游，绝不自动重跑

级联重跑看起来「自动化程度高」，实际是把一次人的决定放大成 N 次无人决定的执行。下游节点的重跑各自消耗真实模型额度、各自产生新提交、各自可能失败并留下保留现场。更关键的是：上游变更未必影响下游——一次纯注释修改和一次接口签名变更，对下游的意义完全不同，而这个判断只有人能做。

因此下游只被标记，标记里指名「哪个上游、从哪个提交变到哪个提交」，让人自己看要不要动。这与 A05 保留现场「标记不删除」、保留账本「超龄超量标记给人裁决」是同一哲学。

### 3. 已合并入默认分支的节点拒绝重跑

一旦节点提交合并进受保护默认分支，它就进入了交付终态。此时「重跑」在语义上是回滚——而回滚是一个完全不同的能力（需要 revert 提交、需要新的审批链、需要处理已发布记录）。

用重跑表达回滚会造成一个危险的中间态：节点回到 `ready`，但它的旧提交已经在 main 上。因此这一条必须硬拒绝，且错误要指名「已进入交付终态」而不是笼统的「状态不允许」。

### 4. 审批失效复用既有漂移检测，不新建机制

`review-subject-binding` 已经把「交付对象在验证批准后改变」这件事处理好了——`closing.spec.ts#subject-drift` 与 `index.ts` 的 `PactFlow delivery subject changed after verification approval; re-confirm the reviewed tasks` 就是现成的。

重跑产生新提交 → 任务集合的 expected commit 变化 → 既有检测自然命中。本 change 要做的是**确保它确实命中**（写对抗性测试），而不是另写一套失效逻辑。

### 5. 不新增事件类型

重跑经既有 `pactflow/node-updated` 表达，授权证据与过期快照走 payload 可选结构化字段。投影形状变化经 DAG 投影 `stateVersion` 升级。

与 `need-comment-threads` 的相反选择一致：重跑是既有领域对象（节点）的状态变化，不是新领域对象。升生产者版本的代价不值得。

### 6. fold 层的授权判定

当前 fold 层拒绝 `succeeded → ready`。改造后 fold MUST 区分两条路径：

- 携带有效授权证据的 `node-updated` → 允许；
- 不携带的 → 继续拒绝。

授权证据必须是**事件里的持久内容**，不能是调用时的内存标志——否则冷恢复重放事件时无法复现判定，投影就不再是纯 fold。这是本 change 最容易做错的地方，需要专门的重放测试：把含重跑的事件流重放两次，断言两次折叠结果一致。

### 7. 论证的诚实性（评审后重写）

首版 proposal 用「`retryNode` 已经复活 failed/cancelled，所以不变量早已不字面成立」来减轻修改架构的分量。评审指出这是偷换：失败终态没有下游依赖，成功终态有。「终态复活被拒绝」保证的是「`succeeded` 意味着永久、下游可以依赖」——这正是本 change 要削弱的东西。

现在的表述：**有意削弱，以三条补偿限制影响**——所有者显式授权（排除一切自动路径，含挂机）、历史全保留、下游只标记不级联。补偿够不够，交架构措辞裁决。这个 change 不靠修辞过关。

### 8. 挂机必须排除在授权路径之外

`need-autopilot` 的既有合同：「在有效授权范围内，宿主 SHALL 支持自动选择合理推荐方案及自动评审」。不排除的话：模型推荐含重跑的方案 → 挂机自动选中 → 重跑被授权，全程没有人——本 change 最核心的约束被既有合同直接打穿。

两个选项：

- **A. 排除**：含重跑的方案不在挂机自动选择范围内，挂机遇之暂停交人。
- **B. 纳入**：承认挂机授权范围内可以重跑，写进合同。

**选 A**。理由三条：重跑是对已成功工作的主动重做，不是挂机的使命「推进到交付」；自动重跑会形成「重跑 → 下游过期 → 重跑下游 → ……」的预算黑洞，而挂机的预算是按「推进」设计的；用户推翻原裁决时做的是人的决定，把它交给自动路径违背了推翻的本意。

代价：挂机在遇到含重跑方案时会停下来等人。这是可接受的——重跑本来就该是人拍板的事。

### 9. 判定不可得即拒绝

「已合并入默认分支」需要一次 Git 祖先链查询。远端不可达时，「查不到就当没合并」是典型的失败开放。本仓纪律是失败关闭：判定不了 → 拒绝并指名原因。这条与 C2 `gitea-review-gate-closure` 的外部手工合并场景耦合——正是因为可能有人在网页上合并了，这条判定才不能省。

## 备选方案（若架构措辞不修订）

**不复活路径**：重跑不改变原节点状态，而是创建一个「继任节点」——继承原节点的依赖、提示与验收标准，原节点保持 `succeeded` 并被标记为「已被继任」。DAG 显式呈现继任关系。

- 优点：不触碰「终态复活被拒绝」，架构文档一字不改。
- 缺点：DAG 会随重跑次数线性增长出语义重复的节点；依赖边需要重接（下游要指向继任节点还是原节点？）；审批链在继任处断裂；「这个需求做了几件事」的读数被污染。

判断：**技术上可行，但代价明显更大**，且把复杂度从一次性的措辞修订转移成了永久的 DAG 语义负担。推荐走主方案。

## 未决问题

- **重跑是否需要单独的预算维度**？当前设计复用 attempt 上限。但「失败重试 3 次」与「主动重做 3 次」共用一个计数，可能让一个反复失败的节点耗尽额度后再也无法主动重做。倾向保持复用（避免第二套上限），但需在真实使用后复核。
- **过期标记的存活期**：下游过期标记是永久的还是在下游重跑后清除？倾向重跑后清除（标记描述的是「相对于当前上游的状态」），但级联清除的边界需要在实施时定清楚。
