# design — fail-open-closure

## 这批修复的共同形态

四路评审交回的高危项分成两类，两类都不是「能力缺失」：

**类一：合同写了失败关闭，实现留了一个放行的口子。** 口子的形式高度一致——一个与被保护的性质无关的前置条件（`gitProviders.length > 0` 之于凭证归属、`spec.expectedBranch !== undefined` 之于摘要完整性），或一个把「我不知道」折叠成「没有问题」的 `catch`（敏感改动清单、CA 材料读取、账本单条记录）。这类缺陷的共性是**在最需要保护的状态下恰好不生效**：空登记表正是升级后的初始态，读取失败正是身份可能被掉包的时刻，账本记录读不出来正是升级刚发生的时刻。

**类二：宿主把自己的失败报告成别人的失败。** 输出预算算错 → 「任务集校验失败」；子进程上限过低 → 「测试套件失败」；墙钟预留算错 → 「模型连接不可用」；敏感改动扫描失败 → 「无改动」。这类最危险的地方在于它不表现为故障，而表现为一个**关于别人的、听起来合理的结论**，于是没有人去查宿主自己。

据此，本 change 的修法统一遵循两条：
1. 失败关闭的判据 MUST 只包含被保护性质本身，不得附加无关条件。
2. 「无法确定」MUST 是一等状态，与「确认为空」在类型上可区分、在呈现上分开表述。

## 为什么对账要问活性，而不是只补 `cleaned`

补 `cleaned` 使账本随正常完成收敛，解决的是无界增长与重放。但它解决不了核心问题：宿主崩溃留下的条目，恰恰是**没有机会补 `cleaned`** 的那些，而那正是 Job 仍在运行的时刻。两者必须都做。

活性读不到时按「仍在执行」处理，代价是一条真正的孤儿责任被多保留一轮（下次启动再对账）；反向的代价是销毁一次真实的模型执行与它已产出的提交。二者不对称，取保留。

## 为什么 Git Secret 用前缀而不是登记表

命名空间内的 Secret 不在 PactFlow 的登记表里——它们由运维在集群侧创建。可用的归属信号只有命名约定，而列举端点本来就在按该前缀过滤。所以本条不是引入新约定，是把**已经存在的约定从界面过滤提升为宿主边界**，并让两处取自同一常量，使其不能单侧漂移。

Git HTTPS 凭证则相反：那里有登记表可查，但「必须属于某个已登记 Provider」会挡住完全合法的形态（一个没有登记 Gitea Provider 的普通 HTTPS 远端）。所以采用否定式判据——**不得是其它已登记资源的凭证**。这精确对应实际威胁（把模型 API Key 当 Git 口令交给对方服务端），且不新增登记要求。

## 构建新鲜度守卫为什么是元测试而不是脚本

50 个 spec 导入 `lib/` 产物，而 `pnpm test` 不构建。探针实测：在 `initialize()` 首行注入 `throw` 后 `domain.spec.ts` 19 例仍全绿——绿来自陈旧产物。这不是慢，是**绿没有意义**。

放进套件本身（而非 `pnpm test` 的前置脚本）的理由：它要保护的正是「有人只跑了 vitest」这一路径，前置脚本对 `pnpm exec vitest run <file>` 无效。`pnpm run check` 先构建，因此收口门禁永远满足它；唯一会红的，正是此前会骗人的那一次。

判据用修改时间而非内容哈希：产物是打包与转换后的结果，与源码无法逐字对照；而「产物比源码旧」这一关系本身就是要断言的全部内容。

## 有意不做

- **不新增事件类型、不升生产者版本。** 唯一新增的持久字段（验证敏感扫描的未知标记、账本的计划子资源名）都是既有负载结构内的可选字段，旧读端解析不失败。
- **不改 `cancel()` 的可达调用点。** 三个调用点当前都带已确认 UID，行为不变；改的是那条不可达分支由「按名删除」变为「失败关闭」，并删除只服务于它的三个私有方法。
- **不动挂机的授权语义。** 拒绝走的是既有的 `block` 通道，不新增状态、不改限额。
