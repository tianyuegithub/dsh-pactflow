# design — gitea-review-gate-closure

## 关键决策

### 1. 等待态经既有事件的 payload 可选字段表达，不新增事件类型

沿用 `artifact-ref-handoff` 的处理：payload schema 非 strict，旧读端剥离未知键即可读新日志，老会话升级插件后不触发生产者声明冲突。投影形状变化经 Delivery 投影的 `stateVersion` 升级表达。

**理由**：等待态是既有收口语义的一个中间态，不是新的领域对象。为它升生产者版本，代价（全量老会话的声明升级路径需重验）远大于收益。与 `need-comment-threads` 的选择相反——那里评论与附件是**新领域对象**，值得升版。

### 2. 复查是「显式触发 + 有界后台复查」，不是阻塞轮询

阻塞轮询会占住收口调用、吃掉取消语义，并且一旦 CI 跑二十分钟就必然超时。有界后台复查的间隔与最大次数取既有运行时合同（`run-time-contracts` 已把时间语义单列为合同），不引入第二套硬编码。

复查次数耗尽**不是失败**——等待态保留，人可以随时再手动复查。这与「保留现场绝不自动删除」同一哲学：耗尽的是自动推进的耐心，不是用户的处置权。

### 3. 合并路径必须与无保护分支路径共用同一段核验

这是本 change 最关键的一条，也是最容易做错的一条。

诱惑在于：等待路径已经拿到了 PR 对象、已经确认了 mergeable，于是顺手在等待分支里写一遍合并与核验。结果就是两套实现，其中一套（新的那套）没有经历过 `git-closing-integrity` 历年积累的对抗性测试——精确 merge SHA 断言、祖先链核验、任务集合对本次基线的精确核验、`close-with-binding-auth` 修复的凭据来源。

因此 spec 里写死「核验实现唯一」并要求测试断言之。

### 4. 外部手工合并：后台不追认，显式请求走既有路径

等待期间有人在网页直接合并，是真实会发生的情况。首版方案写的是「不被追认、要求显式处置」，评审指出它与现有代码打架——`index.ts` 已有 `priorPullRequest?.merged === true → verifyClosingMerged → verifyClosingTaskRefs → 继续`，且这条路径本来就只在下一次 `close_git_need` 调用时走，那已经是显式动作。

精确后的界定：

- **后台复查**发现已合并 → 只标记「已被外部合并」、停止后台复查、不产生交付终态。因为后台复查是无人参与的自动动作，让它追认等于让交付终态在无人核验的自动路径上产生。
- **显式收口请求**（人或模型再调一次收口）→ 走既有 `merged === true` 路径，核验通过才产生终态。**这条路径不重写**——它已经做了 merge commit 精确比对、祖先链、任务集合核验，是 `git-closing-integrity` 历年对抗测试覆盖过的。

于是「显式处置」不是一个新动作，就是「再请求一次收口」。spec 里把这层关系写明，避免实施者以为要造一个新入口。

### 4a. 挂机怎么办

挂机（`need-autopilot`）的合同是「持续推进十阶段直到验证通过的代码合并」，它的进展判定有「连续无有效进展达到上限则阻塞」。等待态是一个全新的「停着但没失败、也不是模型该动」的位置——首版方案完全没提，评审指出实施时要么挂机把它当失败终止、要么在循环里烧 API 配额。

处理：等待态对挂机是**等待外部人与 CI**，与「等待人工决定」同族——不计入无效进展、不唤醒模型、不调 `pactflow_block_autopilot`（那是异常阻塞）。宿主按有界复查合同推进；齐备后走既有收口并按既有「真正完成」条件标记挂机完成；复查耗尽时保持授权与等待态、持久报告，人手动复查后齐备则挂机继续。`need-autopilot` 因此列入 Modified Capabilities。

### 4b. 与 `node-rerun-authorization` 的耦合

该 change 的失败关闭第 2 条「节点提交已合并入默认分支 → 拒绝重跑」，正是为本 change 的「外部手工合并」场景而设（否则该条与「需求处于 closing/deployed → 拒绝」几乎重叠）。两个 change 互为前提，任一先实施均可，但后实施者须复核前者的对应场景仍成立。

### 5. 权限边界：能读的都读，能写的一概不写

宿主读 required approvals、读 status checks、读 PR 状态；不提交批准、不改分支保护、不强制合并、不触发 CI。

这条看似显然，但实现时有具体的滑坡：Gitea API 的 merge 接口带 `force` 与管理员合并选项；`mergePullRequest` 现有实现里已有对 "not in mergeable state" 的重试逻辑（`gitea.ts:326`）——该重试在受保护分支场景下必须收敛为「不可合并就是不可合并」，MUST NOT 演变成绕过保护的循环。实施时需复核这段。

## 不做什么

- **不做 CI 触发与重跑**：检查失败是仓库与 CI 的事，零脉只如实呈现。
- **不做审批人指派与提醒**：需要用户身份目录与通知通道，属新目标。
- **不做 GitHub/GitLab 适配**：Git Provider 抽象保持不变，本 change 只落 Gitea。
- **不做「超时降级为无保护合并」**：任何绕过分支保护的路径都直接违反架构 §4，永久非目标。

## 未决问题

- **后台复查是否默认开启**？倾向默认关闭、由用户在项目配置里开启——默认开启会在无人值守时持续调用 Gitea API，且用户未必期望零脉主动动作。留待实施时按 `run-time-contracts` 的既有语义定。
- **required approvals 的「谁批准的」是否需要记录**？记录审批人身份有审计价值，但涉及把外部用户标识落进 Session Event。倾向只记录数量与达标事实，不记录身份，避免引入用户身份的持久化面。需在实施前确认。

## 验证路径

真实受保护 Gitea 仓库，真实配置 required approvals 与至少一个 status check，真人在网页上真实点批准，真实 CI 产生检查结果。**不走 mock**——这是仓库既有纪律（Git/Gitea/Harbor/K3s 验收必须走真实路径），也是本 change 唯一能证明「等待态真的能等到」的方式。
