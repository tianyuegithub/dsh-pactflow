# design — spec-corpus-corrections

## 判据：哪一侧是错的

四条不一致里，每一条都先回答同一个问题——**spec 与代码，哪一侧承载了错误**——再动那一侧。判据不是「谁先写的」，而是**哪一侧在被真实执行时会造成损害**。

- 复查节奏：spec 要求继承一个并不存在的合同。按 spec 实现意味着把无关的租约参数当成 API 轮询节奏，不合理；代码建立自有合同并写明定尺理由，是正确处置。归档 change 的 tasks 当时就记录了前提有误，只是没回写正文。**改 spec。**
- Agent 触发合并：spec 的 Requirement 正文比它自己的 Scenario 宽。两者不一致时，取窄的那个——因为宽的那句会把一条有人工批准背书的正当路径写成违规。**改 spec。**
- 重跑预算：spec 要求的处置方式会不可逆地摧毁交付终态。这不是权衡，是错误。**改 spec。**
- 保留查询面：同一份 spec 内两条 Requirement 互斥，现网实现必然违反其一。把穷举清单改为「由契约要求」的判据，两条同时成立。**改 spec。**

## 为什么保留「被替换了什么、为什么」

每条更正都在正文里以引用块写明它替换了什么表述、那条表述错在哪。理由是这个 spec 语料库会被后来者（包括模型）当作唯一正文来读：只留下正确的结论，下一个人无从判断它是深思熟虑的还是漏写的，很可能「修正」回去。上一轮评审抓出的四条高危里，就有一条是把 `retryNode` 的写法照搬到前态不同的路径上——正是缺少这种记录导致的。

## 为什么重跑那条用 REMOVED + ADDED 而不是 MODIFIED

MODIFIED 在归档时替换整块，且校验器要求带全原有 Scenario——这是防止意外丢弃的正确设计。但这里要去掉的恰恰是 Scenario「上限耗尽进入持久暂停」本身：保留它的名字再写进相反的内容，会造出一条标题与内容矛盾的 Scenario。REMOVED + ADDED 如实表达「整条替换」，并让被移除的部分在 change 正文里留下痕迹。

## 有意不做

- **不改任何代码。** 本 change 的全部内容是让正文与已交付且经评审的行为一致。
- **不处置祖先链判定那一条。** `node-rerun-authorization` 要求以 Git 祖先链判定「是否已合并入受保护默认分支」并在查询不可得时失败关闭，代码只查本地投影。按 spec 实现是设计变更（同步只读路径引入远端查询），按代码改 spec 是降级一条已写下的失败关闭要求且残余风险真实。这属于目标本身的裁决，已在 proposal 中提请，未在此处单方面处置。
