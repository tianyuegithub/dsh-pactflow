> **状态：提案，等用户裁决（未实施）。** 与 `harden-minimum-validation-policy`（A03-b）耦合：b 定「至少跑什么」，c 定「跑的东西里哪些不可被任务改弱」——建议 b 先行，c 的基线作为 b 策略要求组的一个**宿主自有来源**接入。

## Why

A03 的最后一环：即使有了最小验证策略，**验证命令本身仍来自任务仓/用户配置**——任务改弱测试（或用户配置本身宽松）时，"跑够了验证"依然可能验不住任何东西。宿主侧独立验收基线 = **宿主自有、存储在任务仓之外、任务无法修改**的断言资产（如冒烟脚本/断言命令），收口时在确定候选提交上与任务验证一起运行，产出**独立标识的证据**。它与 A03-d（验证敏感改动可见）互补：d 让"改了测试配置"可见，c 让"无论你怎么改，我自己的断言都要跑"。

已就位：收口在隔离 checkout 的候选提交上执行宿主解析命令（F05）；验证证据结构（`validations`）与执行计数已贯通；配置存储与编辑器模式现成。

## What Changes

- 新增**宿主基线资产**：按工作区登记的一组宿主自有验证命令（存储于 `workspace-projects.json`，人所有、走既有 CAS + 锁；与任务验证命令的登记方式一致但**独立命名空间**）。
- **收口执行**：`closeGitNeed` 的隔离复验在候选提交上**先跑宿主基线、再跑任务验证**；基线证据以 `source: 'host-baseline'` 独立标识，进入 `gitResult.validations` 与 `validationsExecuted` 计数。
- **不可省略**：基线一经登记即每此收口必跑；任务配置、验证策略（A03-b 的要求组）只能**引用**基线，不能替代或跳过它。
- **决策点（proposal 阶段需你定）**：① 基线失败是否阻断收口——**建议阻断**（基线的意义就在于此；若某工作区尚无基线则不阻断）；② 基线命令上限沿用既有验证命令边界（单条 1s–1h、参数 ≤64×4096B）。

## Capabilities

### New Capabilities
- `host-owned-baseline`: 宿主自有验收基线存储于任务仓之外，收口时在候选提交上强制执行并产出独立标识的证据；任务侧不可修改、不可跳过。

### Modified Capabilities
（无——收口执行槽位与证据结构复用既有合同；基线作为验证证据的一种来源，不改变 `git-closing-integrity` 的合并幂等/精确 SHA 语义。）

## Impact

- **配置**：`workspace-projects.json` 增基线资产段（人所有）。
- **收口**：隔离复验增加基线执行阶段；证据带 `source` 标识。
- **客户端**：基线编辑入口（复用验证配置编辑器模式，独立分区呈现「宿主基线」）。
- **测试**：基线执行/证据标识/不可跳过/失败阻断单测 + 收口 e2e（含"任务改弱自己的测试但基线仍拦截"的对照场景）。
- **不做**：不为基线引入新存储位置（复用配置文件与锁）；不让模型提供基线内容；不做基线的自动生成。
