# design — need-attachments

## 关键决策

### 1. 本体走第七类资源，不新建大内容通路

脱敏门、hash 校验、绑定隔离、保留裁决——这四项对附件与对执行日志是同一套要求。另建一条通路等于把四项再实现一遍，且必然出现两套阈值与两份账本。架构 §4「大内容不进有界通道」是不变量，复用是它的正确表达。

### 2. 原生 attachment 为什么不能整个复用，又为什么不能整个不用

**不能整个复用**：`@deepseek-ai/dsh-attachment` 的类型面全是图片语义——`ImageMediaType` 只有四种光栅格式，`EncodedImageAttachment` 要解码归一化，`ImageVariantId` 是图片变体。它是「给提示词附图」的机制，存在 DSH_HOME、绑定对话历史、重发给模型。通用附件（日志、PDF、设计稿）既不是图片，也不该存 DSH_HOME（该存项目绑定的对象存储），更不该自动重发给模型。

**不能整个不用**：它证明 DSH 客户端到宿主有一条原生的字节传输路径。架构 §3 第 10 条要求「全部使用 DSH 原生机制」。在没评估这条路径之前就自建传输，是本批评审指出的最明显的「没先查原生有什么」。

所以：**存储与语义走第七类资源，传输层优先复用原生**。二者是可以拆开的——前提是原生传输层能被插件接入且不强制图片语义。这正是任务 0 要回答的问题。

### 3. 传输层三个候选的取舍

| 候选 | 优点 | 代价 | 何时选 |
| --- | --- | --- | --- |
| 复用原生 attachment 传输层 | 零新协议、符合原生机制要求 | 可能被图片语义锁死、可能有 `maxBytes` 策略限制 | 评估证明可承载任意字节且可接入 |
| 分片经 Remote | 不新增端点、完全在插件控制内 | 分片状态机、重组失败语义、每片 ≤ 硬限带来的往返次数 | 原生不可行 |
| 宿主新增上传端点 | 最直接 | 与「不新增 HTTP 端点」相悖，暴露面扩大 | 前两者均被证明不可行，且须单独评审 |

**为什么不直接选分片**：它完全可行，但它是「插件自建一套原生已有的东西」——如果原生路径可用，分片就是重复造轮子且违反原生机制要求。评估成本远低于分片的实现与维护成本。

**为什么把端点排最后**：`artifact-ref-handoff` 在读取侧已守住「不新增 HTTP 端点」，写入侧开口子会让这条约束失去意义。

### 4. 附件不自动喂给模型

原生 attachment 会把图片重发给模型；通用附件不能这样——一份 50 MB 日志重发给模型是灾难。附件对 Agent 只读 ref 与摘要，内容按需 resolve+校验。这与 `artifact-ref-handoff` 的消费侧协议一致。

### 5. Agent 只读

模型向对象存储写入未经人审的内容，绕过「人决定什么材料进入项目」这一层，且放大脱敏门的暴露面。收益很小（模型产出本就该走节点产物或文档）。与 `need-comment-threads` 中评论可写形成刻意的不对称。

### 6. 事件版本随实施顺序

**顺序已确定（2026-09-15）**：`need-comment-threads` 已先实施并占用 `0.7.0`，因此本 change 升 `0.8.0`。两个 change 各自的词汇表都逐条字面列出、各自钉死老会话可写。任务 3.1 按 `0.8.0` 执行。

## 不做什么

- 不做图片预览与变体：那是原生 attachment 的领域，零脉不重复。
- 不做附件版本：对象 key 含随机段、写后不可覆写，「新版本」就是新附件。
- 不做编辑与物理删除：保留账本裁决。
- 不做跨需求附件库：会引入不归属任何领域对象的内容。

- **媒体类型白名单**：是否限制可上传的类型（如拒绝可执行文件）？倾向不做白名单——脱敏门管内容，类型不是安全边界；但需在实施前确认这不与工作区沙箱策略冲突。
