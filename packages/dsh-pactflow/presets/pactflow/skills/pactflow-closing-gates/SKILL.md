# 收口三层防线

收口 = 把需求成果固化成提交并合并进受保护默认分支。**宿主不信任执行侧**，因此三层递进：

| 层 | 配置处 | 谁执行 | 挡什么 |
|---|---|---|---|
| ① 验证证据 | 宿主验证配置 | Worker / 模型按编号执行 | 「没验证过」——收口要有真实执行记录 |
| ② 最小验证策略 | 收口最小验证策略 | **宿主**核对每交付物的必需证据 | 「验证过但不是必须的那些」——缺失逐项指名阻断，模型不可修改 |
| ③ 宿主基线 | 宿主基线（owner-only） | **宿主**在候选提交上**先于**任务验证执行 | 「任务仓内的验证被绕过或篡改」——命令存在任务仓之外，Worker 够不到 |

三层合起来回答三个不同的问题：证据由谁产生（①）、哪些证据必须存在（②）、独立于任务的最终防线（③）。

## 为什么第三层必须在任务仓外

前两层的证据都来自任务仓内执行。如果验证命令本身写在任务仓里，一个能改仓库的 Worker 就能改验证——那两层挡不住「把测试删了让它变绿」。宿主基线的命令存放在任务仓之外、由宿主在候选提交上执行，Worker 没有路径触及它。

## 收口被阻断时怎么读

- **「缺失逐项指名」**：第 ② 层在说哪些必需证据没有。补的办法是让对应验证真的跑一次，不是去改策略。
- **宿主基线失败**：第 ③ 层在说候选提交没通过独立断言。看基线命令的实际输出，不要绕过。
- **不要为了变绿削弱任何一层**。降低断言、放宽超时、跳过失败项换来的绿，比红更糟——它把「不知道」伪装成「已验证」。

## 受保护分支要求外部评审时

仓库若配置了 required approvals 或 status checks，收口**不会放弃**，而是进入持久的「等待外部评审」状态：宿主创建 PR、保留收口责任、按有界节奏复查，齐备后由宿主完成合并与全部核验。

**不要建议用户自己去 Git 网页手工合并。** 手工合并产生的交付终态宿主从未核验——祖先链没核、任务集合是否精确对应本次基线没核、清理责任没先于交付记录持久化。要等就等，或者请评审者去批准。
