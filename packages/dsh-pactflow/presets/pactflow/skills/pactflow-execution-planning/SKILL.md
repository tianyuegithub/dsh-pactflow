# 执行方案与拆分判据

## 默认：一个完整交付节点

优先**一个完整的交付节点**。实现、测试、修复、文档与交付记录通常是这个节点**内部的验收清单**，不是并列的节点。

以下**都不构成**拆分理由：
- 涉及多个文件
- 分前端与后端
- 步骤有先后

**构成**拆分理由的只有四类：
1. 具体的、可独立并行的收益
2. 不同的权限或环境要求
3. 必要的独立评审
4. 有意义的失败隔离

提出拆分时，同时说明**交接成本、集成成本，以及谁负责集成**。只有一个合理方案时就给一个，不要为了凑数编第二个。

## 方案确认协议

**任何执行代理调度之前**——包括前期调研——必须调用 `pactflow_confirm_execution_plan`，带上：
- 具体的候选方案
- 明确的推荐
- 完整的节点提示词
- 验收标准
- 依赖与代码输入依赖
- 已登记的执行路由

原生选择**就是**对那个具体方案的人工批准。

- `approved` 为 false 时：讨论反馈并**停止执行**。自定义文本或取消**都不是同意**。
- 派发时使用返回的**精确**提示词与路由。
- 范围内重试复用已有批准，不重复询问。
- 任务内容、节点、依赖或执行资源**变化**则旧批准失效，需要重新选择。
- 被选中的方案**已经通过了计划审批**，不要再为它单独发起一次通用计划审批。

## Worker 数量的含义

Agent 组合里的 Worker 数量是**最大并发**，不是「已经在跑的」或「预留的」代理数。

按需启动就绪节点即可，**不要为了填满槽位而拆分或派发**。

## Worker 的职责边界

一个 Worker 拥有**整个有界交付**，包括在范围内修复验证失败，然后才能报告完成。

缺少环境访问权限或范围不清必须**报告**，绝不能藏成成功。
